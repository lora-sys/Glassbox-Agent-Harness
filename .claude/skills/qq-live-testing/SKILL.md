# QQ live testing

Use this skill while implementing a Glassbox feature that needs acceptance through real QQ, when rerunning QQ regressions, or when fixing a failure found by those checks. It guides the workflow. It does not grant permission to send messages, operate a group, change runtime state, or merge.

Before testing, read `AGENTS.md`, the applicable active plan, `docs/tech-stack.md`, `tools/qq-live/README.md`, and `tools/qq-live/HANDOFF.md`. Read [core-rules.md](core-rules.md) and verify its lock with `node .agents/skills/qq-live-testing/scripts/verify-core.mjs`. Review [lessons.jsonl](references/lessons.jsonl) for relevant verified lessons. Run helper coverage with `node --test .agents/skills/qq-live-testing/scripts/helpers.test.mjs` when changing this skill.

The current CLI supports its documented fixed cases, schema-v2 read-only feature cases, and the separately enabled fixed Memory feedback/promote/expire lifecycle through server leases. Review the fixed lifecycle with plan --case memory-lifecycle and supply its hash before running. It uses independent state proof and account-wide unresolved-fixture records. Use reconcile-memory for read-only interrupted-fixture inspection, then its exact approved fixed reject or expire plan for authorized cleanup. It verifies stopped Linux processes, scoped audit and Trace evidence, and final state before releasing the unresolved-fixture guard. Interrupted recovery attempts remain blocked; no blind resend or takeover is supported. CLEANED is cleanup evidence only and never feature acceptance. Follow README for STOP handling and limitations. Schema-v1 free-text scenarios support planning only. Schema-v3 suites may combine read cases with the fixed memory-project-promote-expire and memory-project-feedback-reject families. Select one case per invocation and approve the original suite bytes. Promote/expire requires three distinct Runs; feedback/reject requires two distinct Runs and proof that the candidate is rejected without a promoted Memory. Both require fresh product and Owner cleanup evidence. Neither covers scope isolation or authorization negatives. Reject-family verified lessons remain unsupported and must stay hypotheses. The executable read seed and fixed Memory family do not cover the complete existing-feature baseline. Run coverage against the actual suite and keep missing domains BLOCKED. Follow HANDOFF for these boundaries. If the requested feature has no supported live case or product-evidence check, add the narrow case, observer, and evidence checks to the existing CLI and isolated fixture suite when they fit the authorized implementation scope. Do not treat a transport smoke check as feature acceptance. If the required product path exceeds that scope, use HANDOFF to name the missing contract and owner before continuing. Do not invent a command or claim support.

For an authorized iteration:

1. Record the target feature cases, baseline regression scope, checkout, and exact commit. Use isolated disposable state for automated tests and the repository's established shared service/data directory only for explicitly authorized real QQ acceptance.
2. Run the feature suite and relevant baseline regression before and after a code fix. Use the repository's documented commands, including `npm --prefix tools/qq-live test`, `npm run test:regression`, and focused tests selected by the active plan. Run only documented live cases after explicit authorization for those sends and any group action.
3. Require product evidence for each live PASS. Match the case to the exact Glassbox Run and verify the expected authorization and delivery evidence. A transport result, `doctor`, simulated event, or Bot claim alone is not product acceptance. Follow HANDOFF for FAIL, BLOCKED, INCONCLUSIVE, STOP, cleanup, and bounded evidence-led repair.
4. Fix the demonstrated cause and keep or add regression assertions. Never skip a failed case, weaken an assertion, rewrite evidence, or relabel unknown results as PASS. Record only reusable lessons with `record-lesson.mjs`. Findings without a passing report stay hypotheses. Verified lessons require a hashed successful `qq-live` report whose workspace, runtime, case, authorization, delivery, and exact commit match, plus matching input and delivery events confirmed by the existing `gbxtrace` CLI. The helper stores the report hash and Run ID, not the report or Raw Trace.
5. Clean up only resources created for this acceptance and confirm the test environment is restored. Keep reports local when they contain account or message data. Do not copy credentials, personal messages, screenshots with identifiers, or tokens into a lesson or shared report.
6. Merge only when the feature suite, baseline regression, cleanup, exact tested commit, CI, and PR review all pass, and the user has explicitly authorized the merge. Confirm CI and review apply to that exact commit. After merging, verify the merged commit and repeat the applicable acceptance against it. If any gate is missing or the commit changes, do not merge.

The stable acceptance rules are defined in [core-rules.md](core-rules.md), protected by [core-rules.sha256](core-rules.sha256). Change the core only as an explicitly reviewed policy change and update the lock in the same change. Routine improvements belong in this skill's playbook or append-only lessons. Changes to a secondary playbook require regression evidence. See [lesson-format.md](references/lesson-format.md) for the lesson schema and command. No skill update expands the user's authorization.

Use delivery-check with the original approved suite and a schema-1 reports manifest to rebuild delivery evidence. deliver --live requires existing user merge authorization and performs one exact-head squash merge only after complete coverage, fresh product and cleanup proof, repository validation, fixed GitHub Actions checks, and an independent current-head PR approval. Read its JSON result: an unknown exit does not mean the merge failed. Preserve the PR-wide attempt record and inspect GitHub before any further action. Never retry a merge by changing the suite, report directory, or QQ account.

After GitHub confirms the merge, fetch its actual mergeCommit. Switch the clean acceptance checkout and shared Glassbox service to that exact commit, preserving NapCat and native Pi settings. Install that checkout's dependencies, rerun the full approved live suite, then run postmerge-check with the new reports. DELIVERED requires matching mergeCommit CI and independently observed Runs created after mergedAt. Candidate-head reports do not satisfy post-merge acceptance. The complete feature catalogue still contains planned cases; COVERAGE_GATE remains blocking until every required case is implemented and independently passes.

The fixed qq-group-member-directory-read case uses Owner private chat and test group A only. It checks the complete untruncated Tool result against its byte count and SHA256 and accepts only the memberCount projection. Missing normal group authority blocks the case; do not add authority to pass acceptance. This does not cover member profiles, role changes, or cross-group isolation.

Member-count lessons remain hypotheses until the lesson verifier can independently recheck the count witness. It rejects verified claims when the report or same-Run Raw Trace identifies qq_group_members, including claims that remove the aggregate assertion. A successful live report does not bypass that separate lesson gate.
