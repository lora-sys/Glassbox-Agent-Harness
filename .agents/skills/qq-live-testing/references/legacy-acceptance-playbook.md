# QQ live testing

Use this skill while implementing a Glassbox feature that needs acceptance through real QQ, when rerunning QQ regressions, or when fixing a failure found by those checks. It guides the workflow. It does not grant permission to send messages, operate a group, change runtime state, or merge.

Before testing, read `AGENTS.md`, the applicable active plan, `docs/tech-stack.md`, `tools/qq-live/README.md`, and `tools/qq-live/HANDOFF.md`. Read [core-rules.md](core-rules.md) and verify its lock with `node .agents/skills/qq-live-testing/scripts/verify-core.mjs`. Review [lessons.jsonl](references/lessons.jsonl) for relevant verified lessons. Run helper coverage with `node --test .agents/skills/qq-live-testing/scripts/helpers.test.mjs` when changing this skill.

The current CLI supports its documented fixed cases, schema-v2 read-only feature cases, and the separately enabled fixed Memory feedback/promote/expire and feedback/reject lifecycles through server leases. Review the fixed lifecycle with plan --case memory-lifecycle and supply its hash before running. It uses independent state proof and account-wide unresolved-fixture records. Use reconcile-memory for read-only interrupted-fixture inspection, then its exact approved fixed reject or expire plan for authorized cleanup. It verifies stopped Linux processes, scoped audit and Trace evidence, and final state before releasing the unresolved-fixture guard. Interrupted recovery attempts remain blocked; no blind resend or takeover is supported. CLEANED is cleanup evidence only and never feature acceptance. Follow README for STOP handling and limitations. Schema-v1 free-text scenarios support planning only. Schema-v3 suites may combine read cases with the fixed memory-project-promote-expire and memory-project-feedback-reject families. Select one case per invocation and approve the original suite bytes. Promote/expire requires three distinct Runs; feedback/reject requires two distinct Runs and proof that the candidate is rejected without a promoted Memory. Both require fresh product and Owner cleanup evidence. Neither covers scope isolation or authorization negatives. Verified feedback/reject lessons must select the final `memory-reject` Run and recheck both historical Runs, the fixed Tool evidence, Owner/project/candidate lineage, reject audit, and final absence of pending or active state. The executable read seed and fixed Memory family do not cover the complete existing-feature baseline. Run coverage against the actual suite and keep missing domains BLOCKED. Follow HANDOFF for these boundaries. If the requested feature has no supported live case or product-evidence check, add the narrow case, observer, and evidence checks to the existing CLI and isolated fixture suite when they fit the authorized implementation scope. Do not treat a transport smoke check as feature acceptance. If the required product path exceeds that scope, use HANDOFF to name the missing contract and owner before continuing. Do not invent a command or claim support.

A recent real two-account group doctor passed in about 1.5 seconds. This confirms only that preflight succeeded; it does not establish a group-read feature or complete acceptance.

## Acceptance-memory cleanup and guard recovery

Use this fixed sequence only for the matching acceptance manifest and original reports. Keep the failed report, manifest, account `.memory-pending.json`, and `STOP` unchanged until the evidence is complete. From `tools/qq-live`, first inspect the cleanup plan without sending:

```sh
node cli.mjs cleanup-acceptance-memory --input <manifest-json> [--config <config-json>] [--out <report-directory>]
```

The default is read-only. Review the complete plan and its SHA256. Only an explicit user authorization for the fixed Owner-private cleanup message permits the same command with `--live --approve-suite <plan-SHA256>`. It sends at most one fixed request and independently checks the matching Run, lease, delivery, database state, and cleanup evidence. A `CLEANUP_VERIFIED` result has `cleanupOnly: true` and `featurePass: false`.

For the acceptance-memory manifest flow, if a prior cleanup report says `INPUT_NOT_OBSERVED` even though the message may have been sent, preserve that report. Do not retry or use the no-ingress recovery path. Run the separate read-only completed-cleanup check:

```sh
node cli.mjs reconcile-completed-cleanup --input <manifest-json> --cleanup-failure <failed-report-json> [--config <config-json>] [--out <report-directory>]
```

This command makes no QQ sends. It independently binds the failed report to the exact successful cleanup Run, complete tool-result digest, nine rejection audits, current candidate inventory, persisted lease cleanup, and fresh two-account message reads. It writes a separate `CLEANUP_RECONCILED` receipt and leaves the failed report unchanged. The receipt means cleanup only. It has `cleanupOnly: true` and `featurePass: false`.

After that report is verified, inspect the exact guard and `STOP` archive plan:

```sh
node cli.mjs reconcile-acceptance-memory --input <manifest-json> --cleanup-report <cleanup-report-json> [--config <config-json>] [--out <report-directory>]
```

This command is read-only unless `--live` is explicit. Review its new plan hash. Archiving requires separate explicit authorization and the same invocation with `--live --approve-suite <plan-SHA256>`. It rechecks the original inputs, cleanup Run, product state, lease audit, runtime, pending guard, and `STOP`, then archives the exact guard and `STOP` with a durable receipt. `ARCHIVE_VERIFIED` has `cleanupOnly: true` and `featurePass: false`. It is cleanup evidence, not feature acceptance or a verified lesson.

If an attempt may have sent, or either command reports missing, changed, ambiguous, or unknown evidence, do not retry and do not remove `STOP` or the pending guard. The cleanup CLI refuses a prior send unless the exact prior attempt has a valid no-ingress receipt. The current library exports `createAcceptanceMemoryNoIngressReceipt` and `verifyAcceptanceMemoryNoIngressReceipt` from `tools/qq-live/lib/acceptance-memory-attempt-reconciliation.mjs`; there is no CLI command for creating that receipt. The verifier rechecks the exact report, manifest, runtime, lease audit and matching ingress state. A valid receipt is consumed for at most one retry, with `retry-used.json` persisted before sending. Never fabricate a receipt or treat it as feature PASS.

## Sent pre-Run read with no product ingress

The fixed `ops-status-read` case has a separate cleanup branch when its unchanged report says `INPUT_NOT_OBSERVED`, includes a sent Owner message ID, and has no product ingress or Run. It uses `planPreRunStoppedReport` and `archivePreRunStoppedReport` from `pre-run-stop-reconciliation.mjs` with already connected `{clients}`. There is no CLI command for this branch. Do not send again or use the acceptance-memory no-ingress retry receipt.

The verifier reads only the fixed Owner-Bot private histories, then calls `get_msg` separately on each account-local message ID. It checks the same sequence, time, body digest, fixed lease audit, runtime, and zero marked product Messages and Runs before and after those reads. It preserves the original report. An `ARCHIVE_VERIFIED` receipt may record `actualQqDeliveryVerified: true` only after both accounts match. It must still report `productIngressVerified: false`, `productRunObserved: false`, `featureStatus: INCONCLUSIVE`, and `featurePass: false`. This is cleanup evidence, not feature acceptance or a retry authorization.

## Fixed account read with an observed failed Run

A separate cleanup branch applies only to the fixed `qq-account-status-read` case when its input and one failed product Run are already observed. The Run must have the exact `required_evidence_missing` failure code. `planPreRunStoppedReport` and `archivePreRunStoppedReport` from `tools/qq-live/lib/pre-run-stop-reconciliation.mjs` independently verify the paired actual QQ messages, product delivery and Trace, and revoked temporary lease. Pass the already connected `{clients}`. There is no CLI command for this branch.

The cleanup and archive receipts preserve the original feature outcome as `FAIL` with `featurePass: false`. They do not upgrade the case to acceptance. This branch does not cover other failure codes or custom cases. Missing or mismatched Run, paired-message, delivery, Trace, or lease evidence leaves the pending guard and `STOP` in place. Do not resend the original message. Unknown failures remain blocked.

Keep manifests, reports, receipts, checkpoints, and failed evidence in private durable storage. WSL `/tmp` is disposable: use a persistent Linux home checkout and evidence directory, and verify the checkout, source hash, service PID, data directory, and files again after a WSL restart. A mismatch or missing artifact means the old attempt remains unresolved. Preserve the native Pi configuration and model settings; do not edit Pi model registries, copy credentials, or recreate login state to make a test pass.

The fixed Taste lifecycle has four distinct Runs for positive feedback, candidate promotion, negative feedback and correction promotion that retires the original preference. Preview it with `plan --case taste-lifecycle`. Schema 6 uses the exact `taste-project-feedback-lifecycle` family and keeps approval bound to the original suite bytes. Account-wide `.taste-pending.json` records block sends and delivery until independent reconciliation. Use `reconcile-taste` for supported known fixture cleanup only; unknown sends remain STOP. Cleanup never upgrades a failed feature report. Final family verification must recheck the actual lifecycle output, four scoped product proofs, runtime identity and zero active or pending fixture state before storing PASS or releasing its anchor. This family does not complete broader Taste, scope or authorization coverage.

For an authorized iteration:

1. Record the target feature cases, baseline regression scope, checkout, and exact commit. Use isolated disposable state for automated tests and the repository's established shared service/data directory only for explicitly authorized real QQ acceptance.
2. Run the feature suite and relevant baseline regression before and after a code fix. Use the repository's documented commands, including `npm --prefix tools/qq-live test`, `npm run test:regression`, and focused tests selected by the active plan. Run only documented live cases after explicit authorization for those sends and any group action.
3. Require product evidence for each live PASS. Match the case to the exact Glassbox Run and verify the expected authorization and delivery evidence. A transport result, `doctor`, simulated event, or Bot claim alone is not product acceptance. Follow HANDOFF for FAIL, BLOCKED, INCONCLUSIVE, STOP, cleanup, and bounded evidence-led repair.
4. Fix the demonstrated cause and keep or add regression assertions. Never skip a failed case, weaken an assertion, rewrite evidence, or relabel unknown results as PASS. Record only reusable lessons with `record-lesson.mjs`. Findings without a passing report stay hypotheses. Verified lessons require a hashed successful `qq-live` report whose workspace, runtime, case, authorization, delivery, and exact commit match, plus matching input and delivery events confirmed by the existing `gbxtrace` CLI. The helper stores the report hash and Run ID, not the report or Raw Trace.
5. Clean up only resources created for this acceptance and confirm the test environment is restored. Keep reports local when they contain account or message data. Do not copy credentials, personal messages, screenshots with identifiers, or tokens into a lesson or shared report.
6. Merge only when the feature suite, baseline regression, cleanup, exact tested commit, CI, and PR review all pass, and the user has explicitly authorized the merge. Confirm CI and review apply to that exact commit. After merging, verify the merged commit and repeat the applicable acceptance against it. If any gate is missing or the commit changes, do not merge.

The stable acceptance rules are defined in [core-rules.md](core-rules.md), protected by [core-rules.sha256](core-rules.sha256). Change the core only as an explicitly reviewed policy change and update the lock in the same change. Routine improvements belong in this skill's playbook or append-only lessons. Changes to a secondary playbook require regression evidence. See [lesson-format.md](references/lesson-format.md) for the lesson schema and command. No skill update expands the user's authorization.

Use delivery-check with the original approved suite and a schema-1 reports manifest to rebuild delivery evidence. deliver --live requires existing user merge authorization and performs one exact-head squash merge only after complete coverage, fresh product and cleanup proof, repository validation, fixed GitHub Actions checks, and independently verified review evidence for that exact head. A formal GitHub approval or a recorded full-diff Agent review may supply the review evidence. Run review recording in Linux with the required directory durability. Use record-agent-review --pr <URL> to inspect the exact binding, then record the independently produced review artifact with --artifact and --expected-review-binding. The private receipt and original artifact are rechecked against the PR, base, head, tree and diff before delivery. The receipt records the trusted host operator's attestation; it is not cryptographic reviewer authentication. Unresolved current-head changes requests still block, and GitHub branch rules remain enforced by the exact-head merge command. Read its JSON result: an unknown exit does not mean the merge failed. Preserve the PR-wide attempt record and inspect GitHub before any further action. Never retry a merge by changing the suite, report directory, or QQ account.

After GitHub confirms the merge, fetch its actual mergeCommit. Switch the clean acceptance checkout and shared Glassbox service to that exact commit, preserving NapCat and native Pi settings. Install that checkout's dependencies, rerun the full approved live suite, then run postmerge-check with the new reports. DELIVERED requires matching mergeCommit CI and independently observed Runs created after mergedAt. Candidate-head reports do not satisfy post-merge acceptance. The complete feature catalogue still contains planned cases; COVERAGE_GATE remains blocking until every required case is implemented and independently passes.

The fixed qq-group-member-directory-read case uses Owner private chat and test group A only. It checks the complete untruncated Tool result against its byte count and SHA256 and accepts only the memberCount projection. Missing normal group authority blocks the case; do not add authority to pass acceptance. This does not cover member profiles, role changes, or cross-group isolation.

Member-count lessons remain hypotheses until the lesson verifier can independently recheck the count witness. It rejects verified claims when the report or same-Run Raw Trace identifies qq_group_members, including claims that remove the aggregate assertion. A successful live report does not bypass that separate lesson gate.

Schema-v4 baseline suites add the fixed `history-group-seed-private-recall` family. Follow HANDOFF and the original suite hash, select the family explicitly, and require both fresh Runs. The first group A input supplies the seed marker and real QQ time; the later private query must use that exact source and until bound. Same-second inputs, missing source evidence and checkpoint failures stop the flow without replay. This proves an earlier group message was retrieved, not cross-group isolation. Historical seed-family lessons require independent archived verification of both stages and must select the final recall Run. Missing evidence remains a hypothesis. Removing the source assertion cannot bypass the family check.

Schema-v5 baseline suites also support the fixed history-cross-group-isolation family. It first verifies a group B fixture and then an A-only private query bounded by the earlier input time. Select that family explicitly and use the original approved suite hash. The final verifier rebuilds both stages and rechecks source, complete search results, actual replies and revoked leases. This does not cover revoked authority or the wider provider failure matrix. Every feature case requires independent persisted lease registration, Run binding and revocation proof. Missing proof persists STOP before any further send.

Ordinary read suites verify each actual Run and persisted lease cleanup before sending the next case, then recheck all passing cases at the end. A failed feature assertion ends the round. If the report independently confirms cleanup, repair the demonstrated problem, verify the new clean commit and start a fresh run within the approved suite and active authorization window. A known reply assertion failure may carry CLEANUP_VERIFIED evidence; its acceptance result remains FAIL. Missing Run evidence, unknown sends, timeouts or unconfirmed cleanup retain STOP. Do not delete STOP to retry, replay the original message or treat a cleanup receipt as acceptance. These paths have deterministic fixture coverage; real QQ acceptance remains required.

The default real-QQ baseline is the fixed `qq-transport-smoke` suite. Run `plan --case transport-smoke` and approve its identity-bound hash before `run --live`. It covers private, group A and group B with per-case empty-Tool leases, independent Run and cleanup checks before the next send, and a final full-suite recheck. Its report is `TRANSPORT_ONLY`; it does not count as feature coverage or feature PASS. Missing runtime, approval, or lease management blocks before OneBot connects. Use only the fixed `qq-group-moderation-exact-b` plan for the documented group B flow. It remains a candidate contract until fresh QQ acceptance proves both mutation stages and restoration. Reports from replaced processes, unavailable QQ reads or unsupported merged-forward/media payloads remain hypotheses. The qq-group-a-info-read case restricts Owner private chat to qq_groups/get_group_info for group A. The qq-group-a-root-files-read case restricts Owner private chat to group A's qq_group_files/get_group_root_files. Version 2 retains a complete-page listing digest and separately compares metadata and counts against one independent Bot read. Its metadata digest removes only each file row's top-level file_id; all other returned fields, folder IDs and ordering remain bound. The pinned NapCat creates a fresh randomUUID cache handle for file_id on each read. These handles are not comparable across reads. The actual Tool output retains full byte and digest verification. This case proves returned metadata and counts, not cross-read handle identity. Historical version 1 retains its original full-listing comparison and must not be relabeled. The fixed provider contract returns a default page of up to 50 entries and has no completeness witness in this operation. This case does not prove the entire directory, folder traversal, downloads or file mutations. Reports retain no entry names, IDs, uploader data or raw Trace head. Both actual replies must be a single plain text line QQGROUPFILES <nonce> files=<fileCount> folders=<folderCount>. Unknown reads or changed metadata remain INCONCLUSIVE and are not retried. Archived lessons remain hypotheses without a separate independent historical listing witness. Removing assertions cannot bypass actual same-Run root-list calls.

Linux is the sole runtime and deployment target. Preserve the existing Pi configuration and model capacities. A ready port does not prove the QQ account is online. Check both independent accounts before fresh sends. Persist each account and NapCat configuration in separate fixed directories; do not recreate them during checkout changes. If QQ rejects a saved login session, retain the data and require actual reauthorization. Verify restart recovery separately from directory persistence. An online/good get_status response and matching get_login_info can coexist with native sendMsg result -10003 and profile-query timeouts. Classify an actual rejected send as expired authorization, preserve the pre-Run cleanup-only report, and request QQ reauthorization. Do not count the online flag, a listening port or a historical receipt as proof of current send authorization.

Use natural Owner and user requests for development regression. Keep the permitted group, read or mutation scope, fixed result checks and cleanup requirements explicit. Tool names and provider parameter names are not substitutes for testing normal requests. Keep exact product commands when the protected Action requires a literal command. If the user requires testing before committing, bind uncommitted development source to an immutable source-tree digest and the service's startup identity. Freeze source for each round and independently confirm terminal execution and cleanup before editing. After a fix, recheck the code, calculate the new digest, switch only Glassbox and verify readiness before a fresh round. Preserve the existing clean-commit delivery gates; development results cannot count as release or post-merge acceptance. Diagnose a refusal through glassbox-ops before retrying. Record only known fixed refusal categories, never protected inputs. Do not infer the exact failed constraint from a generic acceptance_lease_denied result.

An authorization DENY remains a DENY. The observer may recognize an excluded protected source only through its exact durable `authorization.filtered` witness, produced in the same transaction at a fixed conversation-history, task-list or ops-health exclusion branch. The witness must bind the current Run, Principal and original source-read decision. Preserve raw decisions and distinct exclusion receipts. Execution and delivery denials, approvals, unknown actions, missing or mismatched witnesses remain INCONCLUSIVE. Never backfill a historical witness to upgrade a failed Run. Diagnose this boundary through glassbox-ops and Issue #143; verified lessons still require archived evidence under lesson-format.md.

Use the actual EffectiveToolSurface contract when inspecting transport evidence. Its selected array records the selected Tools; selectedCount is not a field. Empty selected and authorizedTools arrays, an exact empty acceptance lease, and no Tool calls must agree. Malformed or missing selected data in a present surface remains unverified. Preserve failed reports and verify exact cleanup before resolving STOP and sending a new message.

For a fixed Owner-private case that the QQ interface explicitly rejected before ingress, use `pre-run-stop-reconciliation.mjs` only after independent evidence confirms no incoming message or Run. Its `planPreRunStoppedReport` is read-only. `archivePreRunStoppedReport` requires the exact reviewed plan hash, persists an archive intent before moving STOP, and writes a cleanup-only receipt only after rechecking the original report and archived STOP. After a crash, keep the evidence and resolve the intent through independent verification; do not remove it manually. `ARCHIVE_VERIFIED` is not feature acceptance and must keep `featurePass: false`.

For repeated invalid QQ arguments, distinguish Pi schema validation, lease admission and actual Provider execution. `tool_call` alone is not execution proof because Pi emits the start event before validating arguments. Inspect the selected Tool definition and same-Run result through glassbox-ops. The real adapter's `session_start.toolSchemaEvidence` fingerprints the selected names, descriptions and parameters passed to Pi; it does not attest the Provider wire payload. Compare the source and definition fingerprints before blaming the model or accepting a retry. Preserve native Pi settings.

Exact acceptance leases project compatible Action, Resource and input constraints into model-visible capability schemas. Private managed-group listing uses an empty object; private provider reads require their authorized group ID, and group reads derive it from the trusted location. An unavailable lease or incompatible schema must fail closed. Call-time authorization remains independent. A narrowed schema does not guarantee that a model will always submit valid arguments.

Group-info and root-file evidence may include at most three paired pre-provider failures with the fixed validation or input-mismatch categories, followed by one matching successful terminal read. Unknown failure categories, unpaired events, multiple successful reads, mismatched groups or missing independent Provider witnesses remain unverified. A successful retry never changes the original failures. These candidate changes require fresh real acceptance before they count as verified lessons.

Use an existing bound safe request witness or independently prove the exact execution-time lease constraint and its application to the successful call. If that chain is unavailable, keep the feature unverified. Never write a reconstructed prompt into historical Raw Trace, infer it from the image, or bypass the media guard to regenerate. Any future request witness must retain only safe hashes and byte counts, with Run, Tool call and Asset lineage.

A missing historical witness must not be reconstructed or backfilled. Verify cleanup independently and archive only through the dedicated reconciliation contract before starting a new family. Returning unknown after a confirmed send with failed evidence persistence must prevent automatic resend.
