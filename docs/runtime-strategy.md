# Glassbox runtime strategy

Status: CURRENT DIRECTION

This document defines the ownership boundary between Glassbox, Pi, Lora PI Kit, and other execution runtimes.

It does not change the active Plan 03 implementation scope.

## Decision

Glassbox remains the product and trust boundary.

Pi is the preferred upstream foundation for the future local Agent runtime path.

Lora PI Kit is the owned configuration and extension layer that adapts Pi to the maintainer's workflow.

Codex and Claude Code remain supported execution runtimes where they provide useful compatibility, specialist behavior, fallback, or differential Eval coverage.

The intended direction is:

```text
Glassbox
  product identity
  authorization
  conversation
  persistence
  trace
  workbench
        |
        v
Glassbox Runtime Boundary
        |
        +-------------------+-------------------+
        |                   |                   |
        v                   v                   v
Pi + Lora PI Kit         Codex              Claude Code
preferred local path     adapter             adapter
        |
        v
upstream Pi
```

Glassbox is not a Pi wrapper. Pi is not the Personal Agent identity.

## Ownership

Glassbox owns product semantics that must stay stable even if the execution runtime changes:

```text
Agent identity
User and Principal
Authorization
Conversation
Durable product state
Run identity
Raw Trace and authorization evidence
Memory and Asset visibility rules
Workbench and public product APIs
```

Lora PI Kit owns reusable Pi customization:

```text
Pi extensions
Pi package manifest
selected skills
prompt templates
runtime presets
model and thinking profiles
observability hooks
notification hooks
project bootstrap
compatibility checks
install, update, and doctor scripts
```

Upstream Pi owns its runtime, Agent loop, package system, Extension API, tool execution primitives, model support, TUI, SDK, and RPC behavior.

Existing Codex and Claude Code adapters keep runtime-specific protocol behavior close to those integrations.

## Lora PI Kit is a separate owned layer

Do not copy Pi source into Glassbox to create Lora PI Kit.

The intended repository boundary is:

```text
earendil-works/pi
      |
      | upstream releases and APIs
      v
lora-sys/lora-pi-kit
      |
      | configured Pi capabilities
      v
Glassbox runtime integration
```

`lora-sys/lora-pi-kit` is a planned owned repository. Create it when the first concrete Pi integration slice starts. Do not add a fake dependency before that repository and its compatibility contract exist.

Pi packages can bundle extensions, skills, prompt templates, and themes. Lora PI Kit should use that package mechanism first. Global or project settings stay in the Pi configuration layer and should be installed or generated by the kit's bootstrap tooling.

The existing `lora-sys/skills` repository remains the canonical source for reusable Agent Skills. Lora PI Kit may select or install those skills, but should not duplicate their source by default.

## Extension first, core patch last

When Lora PI Kit needs a capability, use this order:

```text
Pi setting or project config
Pi package resource
Pi Skill
Pi Extension
Pi SDK or RPC integration
small upstream contribution
local core patch only when no supported boundary can implement the requirement
```

A core patch must have a concrete failing requirement and a compatibility test. Do not fork Pi merely to change defaults or add workflow behavior that the package or Extension API already supports.

If a core patch becomes necessary, keep it small and record:

```text
upstream commit
patch purpose
why Extension, SDK, or RPC was insufficient
test that proves the requirement
rebase or removal condition
```

## Upstream references are evidence, not product code

The repository `upstream/` directory stays read-only reference material.

Pi belongs there as the primary runtime reference. T3 Code, OpenHarness, OpenSquilla, Token Monitor, AGY, Inspect AI, and other projects remain mechanism references for specific boundaries.

The relationship is:

```text
upstream references
      |
      | research and selective ports
      v
Lora PI Kit or Glassbox-owned boundary
      |
      v
production behavior
```

Production code must not import from `upstream/`.

A mechanism that belongs to Pi workflow customization should land in Lora PI Kit. A mechanism that changes Glassbox product semantics, authorization, durable state, or evidence stays in Glassbox.

## Runtime boundary

Glassbox should expose one product-owned execution contract above concrete runtimes.

The contract should normalize only what Glassbox needs, for example:

```text
start or resume execution
send user input
receive normalized events
request approval
stop or cancel
usage metadata
runtime health
runtime identity and capabilities
```

Do not force every runtime to pretend it has identical tools, sessions, permissions, or lifecycle behavior.

Provider-specific behavior remains inside the corresponding adapter.

## Security rule

Glassbox authorization always wins.

Pi extensions, skills, prompts, runtime settings, Codex configuration, Claude Code configuration, and future workers cannot expand the caller's Glassbox permissions.

The order remains:

```text
resolve Principal
-> authorize
-> build authorized Context
-> choose runtime and execution policy
-> execute
-> record evidence
```

Runtime configuration never becomes an authorization source.

## Current phase

Plan 03 does not migrate the runtime.

Plan 03 continues to prove:

```text
Identity
-> Authorization
-> Conversation
-> Turso persistence
-> Run and Authorization Trace
```

Existing Codex and Claude Code regression paths remain intact during P3.

The Pi and Lora PI Kit direction becomes executable after the P3 trust boundary is stable. The first integration slice should prove a small vertical path rather than rewrite all existing adapters.

A useful first slice is:

```text
Glassbox Run
-> Pi runtime adapter through a supported SDK or RPC boundary
-> Lora PI Kit loaded as Pi configuration and package resources
-> normalized events and usage
-> existing Glassbox authorization and Trace
```

Only after that path passes focused tests should shared runtime behavior move away from older adapter-specific implementations.

## Migration rule

Do not perform a big-bang migration.

Move one capability at a time and compare behavior against the current runtime path.

Keep Codex and Claude Code available until Pi plus Lora PI Kit covers the required behavior and Eval shows no unacceptable regression in task success, authorization invariants, trace quality, latency, and cost.
