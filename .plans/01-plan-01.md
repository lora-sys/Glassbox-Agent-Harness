# Plan 01 — First real Glassbox loop

Status: Draft. Roadmap position: P0 / P0.1 (in Review).
Source of truth for this plan: Notion `04 — Delivery → Plan 01 boundary`.
This file is the decision snapshot. Notion keeps product direction and status; `AGENTS.md` keeps stable contributor rules; code and tests become truth once behavior exists.

## Summary

Prove that one real Codex task can enter Glassbox, become understandable and steerable on a tldraw Canvas, and leave a real result plus a minimal Trace. This is the P0 milestone. If the loop is not clearly more useful than reading a scrolling transcript, stop and fix the basic loop before adding research features.

## Motivation

Glassbox's whole thesis is that Agent work should not disappear into a scrolling chat log. We do not know if the thesis holds until a real Run becomes understandable, steerable and inspectable on Canvas. Everything in P1 (researchable workbench) and P2 (experiment and eval lab) depends on this loop being real. P0 exists to fail fast: build the thinnest end-to-end path, prove it, and let the first real provider teach us the contracts before we abstract.

## Goal

One Run of a real Codex task against a controlled repository with a small real bug. The user can start the run, watch meaningful work appear on Canvas, select and inspect a work object, stop the run, send one steering instruction, and reopen the completed run and still understand what happened. The run leaves a real result (artifact or diff, test result, final state) plus minimal Trace.

## User flow

1. User picks the controlled demo repo and bug task in Glassbox.
2. User starts a Codex run.
3. As Codex works, meaningful work objects appear on Canvas: task, current work, at least one artifact or file change, a real test result, a final result, and a trace summary.
4. User selects a work object. The Inspector shows the deeper facts behind it.
5. User stops the run.
6. User sends one steering instruction. The run continues with that input.
7. Run completes. User refreshes or reopens the session and can still reconstruct what happened from Canvas and Trace, not from chat history.

## Scope

In:
- Codex App Server as the only provider.
- tldraw Canvas as the only surface.
- One controlled demo repository with one real, reproducible bug and test.
- Minimum Canvas object set needed to show the flow above.
- Inspector for the selected object, backed by minimal Trace facts.
- Raw Trace plus a small derived-state model, persisted so refresh and reopen keep understanding.
- Explicit Stop and one explicit Steer action.
- One or two editable research objects wired end to end. Plan and Context are the leading candidates.
- P0 security model preserved: no auto-approve, no silent Context from visible content, risky actions inspectable, Raw Trace not rewritten.

Non-goals:
- full Experiment, Variant, or Eval UI.
- repeated `Run x N` or benchmark datasets.
- Agent Team, 3D Agent World, Voice.
- universal provider abstraction. Only Codex.
- full cost optimization dashboard.
- custom Agent loop.
- remote access, multi-user, multi-Agent isolation.
- a second provider.

## Settled decisions

These are settled in Notion and carried into this plan. They are not re-litigated here.

- First provider: Codex, via Codex App Server, because Glassbox needs lifecycle, streamed events, interrupt, approvals and steering. SDK only for a narrow spike if needed. (Notion: Decision log, Runtime and Trace)
- Web direction: TanStack, not Next.js. (Notion: Decision log, Technical stack)
- Toolchain: Vite+ with `vp`, subject to P0.2 repo verification. (Notion: Decision log, Technical stack)
- Canvas base: tldraw, reusing Agent Starter Kit patterns for Canvas context, selection, typed actions and streamed updates. (Notion: References and history)
- Runtime layer: Effect v4 is an approved direction at the provider boundary only. P0 pins one exact RC version and proves one decode path before spreading it further. (Notion: Technical stack and toolchain, P0 adoption gate)
- Two records: Raw Trace is evidence and is not editable. Glassbox derived state is interpretation and is re-derivable. Reconstructing a Run must not depend on Canvas layout. (Notion: Runtime, Codex and Trace, Two records)
- Canvas rule: spatial relationship does not imply execution. Only explicit Actions change execution. Edit freely, execute explicitly. (Notion: Canvas world and interaction rules)
- tldraw Shapes are a projection of Glassbox objects, not the domain model. Domain objects are defined independently so a later 3D view can render the same objects. (Notion: Decision log, Canvas)
- Chat is optional. Reuse a mature Chat component. Do not build one. (Notion: Decision log, Chat)
- Security: P0 is local-first, single-user, single-Agent, single-repo. `AGENTS.md` handles contributor safety. The Notion Security model page handles runtime trust. (Notion: Security model, Status and P0 rules)
- Research objects (Prompt, Plan, Context, Skill, Tool Config, Artifact) can become inspectable and editable. Editing creates a Revision. A change affects execution only after an explicit Action. A Run records the exact revisions it started with. (Notion: Decision log, Editable research objects)
- First demo: a controlled repo with a small real bug that has clear reproduction and test, not an open-ended repo. (Notion: Decision log, Product and first loop)
- Visual direction: Modern Ink Editorial. Paper background, ink text, rare amber for attention or action. Tokens are defined in Notion `Visual and UX direction`. (Notion: Visual and UX direction)

## Reused mature implementations

Glassbox connects to and reuses existing open-source projects instead of rebuilding overlapping capability. These are settled in Notion `References and history`.

- Codex App Server — the first provider runtime, connected not rebuilt. Glassbox sits above it for lifecycle, streamed events, interrupt and approvals. Plan 01 does not build an Agent loop.
- tldraw plus Agent Starter Kit — the Canvas base. Canvas context, selection context, viewport context, typed Agent actions and streamed update patterns are used as implementation material. Glassbox owns product objects and research semantics on top.
- Effect v4 — the type-safe runtime and boundary tool at the provider boundary, adopted narrowly first.
- DeepSeek Harness — a later connected runtime candidate, not P0. Its session log, prompt assembly, tools, skills and plugin concepts show what a connected harness already provides.
- T3 Code — a similar-scope reference project. Carry over its process lessons (build one real path first, let the first provider teach the contract, do not design a universal provider abstraction early), do not copy code.

Rule: do not rebuild capability that an existing open-source project already provides. Connect or reuse first; abstract only when a second real case forces it.

## Risky seams

- S2 and S3 are foundation slices, not vertical. Unified workflow prefers vertical slices. Justification: the first loop has no surface to be vertical against until a minimal runtime and web skeleton exist. Keep these skeletons as thin as possible and switch to vertical slices from S4 on.
- Effect v4 is RC. If the one prove path (Codex event, Schema decode, typed event or typed failure, derived state, focused test) adds more ceremony than information, limit Effect rather than forcing the codebase into it. This is an explicit decision gate, not a default.
- The Codex spike must verify security-relevant facts (approvals, filesystem, network, interrupt, persistence, secrets in events) before any runtime behavior is treated as settled. Do not invent those answers in architecture.
- Visible does not mean trusted. The first Canvas will show repo content, Codex output and artifacts side by side. The default that selection or proximity does not grant Context must hold from S3 on, not be bolted on later.
- Raw Trace rewrite risk. The derived-state reducer will be tempting to fix up history to match the UI. The reducer may re-derive, but must not rewrite evidence. Add a test for this early.
- Universal-provider abstraction drift. With only Codex, it is easy to design a Provider interface that is really just Codex in disguise. Do not build it. Let a second real provider force the contract later.

## Validation

Per Unified workflow: the smallest test that can disprove the current change. Typical order: focused unit or behavior test, then typecheck or lint for changed scope, then integration test for the seam, then real browser or runtime verification when behavior depends on it, then full CI before merge.

Specific to this plan:
- Effect decode path: one focused test that feeds a real Codex event shape and asserts the typed event or typed failure.
- Persistence (S5): a test that reopens a completed run from disk and asserts reconstruction does not read Canvas layout.
- Trace integrity: a test that asserts the reducer cannot mutate stored Raw Trace.
- Canvas rule: a test that moving, grouping or connecting objects does not emit an execution-changing command.
- Steering (S6): a test that Stop and Steer produce the right Glassbox command and Codex call.
- Demo (S8): the real end-to-end run against the controlled repo, recorded as a short video because it involves motion, streaming and interaction.

Async tests wait on real completion signals: event, promise, state transition. No arbitrary sleeps.

UI slices must be verified by the implementing agent (claude code) using browser automation such as Playwright. The agent launches the browser, drives the real flow, and checks whether the slice goal is reached. If the goal is not reached, the agent keeps iterating on the implementation until it is. This applies to S3, S4, S6 and S8. Per AGENTS.md, test both the underlying Glassbox state and the visible Canvas behavior when both matter.

## Done criteria

Plan 01 is Done only when all are true:
- A real Codex task runs against a controlled repo with a real small bug and a real test.
- The run shows meaningful work on Canvas: task, current work, at least one artifact or file change, a real test result, a final result, and enough Trace to inspect what Codex did.
- The user can start, watch, select and inspect, stop, steer, and reopen the run and still understand it.
- Refresh and runtime restart do not destroy understanding. Reconstruction does not depend on Canvas layout.
- Raw Trace and derived state are separate. Raw Trace is not rewritten.
- No provider permission request is auto-approved. Visible or selected Canvas content does not silently become Context. Risky actions remain inspectable.
- One or two editable research objects are wired end to end through an explicit Action.
- Focused tests pass. Affected typecheck and lint pass. CI is green. PRs reviewed and merged.
- Acceptance question answered clearly yes: after using the demo, can someone understand and steer the work better than from a scrolling transcript alone?

If the answer is not clearly yes, stop and fix the basic loop before adding research features.
