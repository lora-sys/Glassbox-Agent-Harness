# Task: S2 / T2.3 — Effect Schema decode adoption gate (apps/server)

T2.2 adapter is done: apps/server can spawn codex app-server, run a read-only turn, stream events, and interrupt. The adapter currently passes raw JSON objects around. This ticket proves that Effect Schema adds value at the provider boundary by decoding those raw events into typed structures with typed errors.

## Goal
Implement one narrow Effect Schema decode path for Codex events, plus a focused test that proves it works against a real event captured from T2.2 or S1. This is the P0 adoption gate: if this path is clearer than plain TS, keep Effect; if not, limit its use.

## P0.2 verified Effect fact
- Effect v4.0.0-rc.112 is installed in apps/server (via the root workspace install).
- API surface confirmed: Schema, SchemaAST, SchemaParser, SchemaIssue, Effect<Success, Error, Requirements>, Cause, Exit.

## Steps
1. apps/server/src/codex/schema.ts: define Effect Schemas for at least these event kinds (plain TS interfaces first, then Schema.make):
   - ThreadStarted (thread.id, thread.status)
   - TurnStarted (turn.id, turn.status)
   - ItemStarted (itemId, type, status)
   - AgentMessageDelta (itemId, delta text)
   - ItemCompleted (itemId, status)
   - TurnCompleted (turn.id, turn.status, turn.durationMs, turn.usage)
   - FileChangeRequestApproval (threadId, turnId, itemId, startedAtMs, reason, grantRoot)
   - TurnInterrupted (turn.id, status = "interrupted")
   Use Schema.Struct for each, with exact: true where it helps.
2. apps/server/src/codex/decode.ts: a decodeEvent(raw: unknown): Effect<CodexEvent, Schema.ParseError> function that inspects the JSON-RPC method field and delegates to the right Schema.decode. Return a tagged union CodexEvent with a type discriminator for each event kind.
3. apps/server/src/codex/adapter.ts: integrate the decoder. When the adapter receives a JSON-RPC notification, pass the params through decodeEvent before emitting to handlers. If decode fails, emit a typed decode error instead of a raw parse crash.
4. Add a focused test file apps/server/src/codex/decode.test.ts. Use real JSON payloads captured from T2.2 /run-test or from the S1 raw_stdio.jsonl (read .plans/findings/01-p0.3-codex-spike.md and spike logs under /tmp/glassbox-codex-spike/ if needed). For each schema, assert that Schema.decode succeeds on a real payload and that typed fields are accessible. For one deliberately malformed payload, assert the decode returns a Schema.ParseError (typed failure).
5. Run the test and confirm it passes.

## Adoption gate criterion
After this ticket, we should be able to answer:
- Does Effect Schema make the event boundary clearer than plain JSON.parse plus runtime checks?
- Does the typed failure (Schema.ParseError) catch malformed events before they become Glassbox state?
- Is the ceremony worth the information for this one path?

Answer these in the findings (not in code).
