# Task: P2.0 spike — T3 Code + Claude Code headless protocol study (read-only + vendoring)

This is a research and vendoring task. You may write ONLY to: .plans/findings/02-p2.0-claude-code-spike.md, .plans/findings/_p2.0-progress.md, and upstream/t3-code/. No source code changes, no business code, no server or web modifications.

## Mission
Glassbox is adding a second provider (Claude Code) behind a thin adapter interface. Before any code, answer the protocol questions with cited evidence and vendor the reference implementation.

## Questions to answer (cite a source for every factual claim; mark unknowns "unverified")
1. How does T3 Code spawn and drive Claude Code? CLI subprocess, Agent SDK, or something else? Name the exact files/mechanisms in its source.
2. What does `claude -p --output-format stream-json` emit? Document the event shapes (init, assistant, tool_use, tool_result, result, partial streaming deltas if `--include-partial-messages` is used). Prefer copying real event samples from T3 Code source or running a harmless `claude -p "say ready" --output-format stream-json` yourself.
3. Permission model in headless mode: can permission requests be answered per-request (mapped to Glassbox's decision flow), or only via coarse permission modes (`--permission-mode`, `--allowedTools`, settings)? Which modes exist and what do they allow? Identify the exact flag/protocol surface T3 Code uses to pass permission configuration per session.
4. Session resume: how do `--resume` / `--continue` / `--session-id` work, and how do they map to Glassbox's thread/turn model (one claude session = one thread; each turn = one -p invocation? or a persistent process?).
5. Writable-root equivalent: how does T3 Code or claude CLI scope writes to one repo (cwd + settings + allowedTools)? What is the safest configuration that guarantees a real repo is the only writable target?
6. Which input object is the natural next editable one for Claude Code (appended system instruction via --append-system-prompt? a session context file? CLAUDE.md?)? Recommend one with reasoning.
7. Codex panel surface: list the codex app-server options worth exposing in Glassbox's session-entry permission panel (approval policy values, sandbox policy values, writableRoots), from the existing apps/server/src/codex code and S1 findings (read .plans/findings/01-p0.3-codex-spike.md and apps/server/src/codex/adapter.ts).
8. For each answer, note how T3 Code implements it, so later slices copy proven code from upstream/t3-code/ instead of inventing.
