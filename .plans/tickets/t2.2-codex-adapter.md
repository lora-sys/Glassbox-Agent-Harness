# Task: S2 / T2.2 — Codex App Server adapter (apps/server)

T2.1 skeleton is done: apps/server (@glassbox/server) runs an empty HTTP shell on port 3030, with effect@4.0.0-rc.112 installed and @glassbox/contracts + @glassbox/shared workspace links resolving. Now build the Codex adapter. Plain TypeScript for this ticket; the Effect Schema decode adoption gate is T2.3, not here.

## S1 verified protocol to implement (from .plans/findings/01-p0.3-codex-spike.md, codex-cli 0.149.1)
- Spawn `codex app-server` as a child process, capture its PID. JSON-RPC 2.0 over stdio, newline-delimited JSON.
- `initialize` request with protocolVersion, capabilities, clientInfo. Then send `initialized` notification. Server returns serverInfo and codexHome.
- `thread/start` with a client threadId. Receive `thread/started` notification carrying the SERVER-assigned thread UUID. Use that server UUID in all later calls, not the client id.
- `turn/start` with `threadId` (server UUID) and `input: [{type:"text", text:"..."}]` (NOT a prompt string) and `sandboxPolicy: {type:"readOnly"}` and `cwd`. Receive streamed notifications: `turn/started`, `item/started`, `item/agentMessage/delta`, `item/completed`, `turn/completed` (with status and token usage).
- `turn/interrupt` requires BOTH `threadId` and `turnId` (both server UUIDs). The turn ends with `turn/completed` status "interrupted".
- Approval requests arrive as server-initiated JSON-RPC requests: `item/commandExecution/requestApproval`, `item/fileChange/requestApproval`, etc. The adapter must NOT auto-approve. Surface them as events to a handler. Default behavior: do not respond with accept (leave pending, or respond decline if a turn must end). This respects the Security model: Glassbox must not silently widen Agent authority.

## Goal
A CodexAdapter in apps/server that can: spawn app-server, do the initialize handshake, start a thread, start a read-only turn, stream events to a handler, interrupt a turn, and surface approval requests without auto-approving. Expose it through HTTP endpoints so it can be exercised.

## Steps
1. apps/server/src/codex/adapter.ts: a CodexAdapter class. Constructor spawns `codex app-server` (capture PID). Implement JSON-RPC over stdio: a request/response correlator by id, and a notification dispatcher. Methods: initialize(), startThread(), startTurn(input, sandboxPolicy, cwd), interruptTurn(threadId, turnId), stop() (kill the spawned PID).
2. apps/server/src/codex/types.ts: minimal TS types for the events and methods above (plain TS, Effect Schema comes in T2.3).
3. apps/server/src/index.ts: keep the existing health endpoint. Add POST /run-test that starts a thread, starts a read-only turn with cwd /tmp/glassbox-t2.2 and a simple prompt like "say ready", collects the event stream for up to ~30s (or until turn/completed), and returns a JSON summary: threadId, turnId, event counts by type, the final turn status and usage, and any approval events seen. Add POST /interrupt that interrupts the current turn.
4. The /run-test turn MUST use sandboxPolicy readOnly and cwd /tmp/glassbox-t2.2 (create that empty dir first). Do not let codex write the user real filesystem.
5. On adapter stop or process exit, kill the spawned app-server PID you captured. Do not kill any other process.

## Verify
- Start apps/server. POST /run-test returns a real event stream summary from codex (item/agentMessage/delta count > 0, turn/completed with a status). This proves the adapter talks to a real app-server.
- POST /interrupt during a long turn returns success and the turn ends with status interrupted.
- If an approval request fires during /run-test (unlikely with readOnly + simple prompt, but possible), the adapter does NOT auto-approve; the response lists the approval event and says it was left pending.
