# Task: P2.3 — Secret screening at the surfacing layer (dedicated safety slice, test-heavy)

Glassbox will be pointed at real repos (Phase 2 goal). Provider events and tool outputs can contain secrets (API keys, tokens, .env contents). Raw trace files are evidence and are never rewritten; screening happens at the surfacing layer so no secret is ever rendered or shipped by an API.

## Evidence rule (AGENTS.md)
Preserve evidence: raw trace on disk stays byte-identical. Screening transforms what derived state and the HTTP/WS APIs return, never what the trace store appends. .glassbox/ is gitignored; at-rest encryption is explicitly out of scope (owner accepted).

## Steps
1. Create apps/server/src/screening/ with a pure screening module: screenText(s) -> {text, hits} and a deep screenValue(v) for JSON structures. Patterns at minimum: OpenAI/Anthropic/StepFun-style keys (sk-...), GitHub tokens (ghp_, github_pat_), AWS keys (AKIA...), Slack tokens (xox...), JWTs (eyJ...), generic Bearer/Authorization headers, key=value pairs for KEY/TOKEN/SECRET/_password, and long hex/base64 strings tagged as suspicious. Keep the list data-driven (one array of {name, regex, redaction}) so adding patterns is trivial.
2. Redaction format: keep a short recognizable prefix plus [REDACTED:<pattern-name>] (for example sk-abc...[REDACTED:openai-key]) so the Inspector stays useful while the secret is gone. Configurable strictness later; one level for now.
3. Enforce at every surfacing point: broadcastDerivedState payload, GET /state response, GET /trace response entries' params, and WS event payloads (broadcastEvent). The trace store append path must NOT screen (evidence). Screen once at the API boundary, not at every call site: wrap the response serialization points in apps/server/src/index.ts and ws/server.ts.
4. Inspector caveat: the web Inspector reads GET /trace to show trace facts. Screening /trace output means the Inspector shows redacted facts, which is correct for real repos. Verify the Inspector still renders sensibly with redacted content (short prefix + tag).
5. Tests (vitest, realistic fixtures, no real secrets): a fixture trace containing planted secrets of each pattern (clearly fake: sk-test-FAKE..., ghp_FAKE...), asserting: raw trace file keeps the secrets (evidence intact), GET /trace response has them redacted, derived state broadcast has them redacted, false positives stay unredacted (for example the words "token count", a 32-char git sha, normal hex colors, code samples discussing regexes), and the redaction is idempotent (screening already-screened text changes nothing).
6. Wire the screening into both providers' paths (codex + claude-code share the same surfacing points, so one integration covers both; assert this with a test per provider if the paths differ).
7. Append progress to .plans/findings/_p2.3-progress.md as you go.

## Safety
- Modify only apps/server (new screening dir, index.ts, ws/server.ts, trace read path) + tests. No web changes needed (it consumes screened APIs unchanged), no AGENTS.md, no Notion.
- Do not modify the trace store append path.
- No git operations (the owner commits).
- Follow AGENTS.md.

## Working style
Budget: within 45 minutes. Append progress per step. This slice is test-heavy: the fixture suite is the deliverable as much as the code.

## When done
Print: the pattern list, the enforcement points, the test summary (including evidence-intact and false-positive assertions), and the vitest summary.
