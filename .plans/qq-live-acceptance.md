# QQ live acceptance

Scope: provide a project-level real QQ acceptance workflow for development Agents. Each delivery must test the new or changed functionality and the existing QQ regression baseline, inspect independent product state and Trace, repair demonstrated failures, and repeat acceptance for the final clean commit. The original private and two-group round trips are transport prerequisites, not complete feature acceptance. Moderation uses a separately consented ordinary test member. No additional model Agent or provider configuration is introduced.

Use the Owner's existing Pi configuration as the model and credential source. Do not copy credentials into Glassbox model profiles or keep a second provider configuration. Native Pi context and output ceilings are independent positive capabilities. Equal ceilings must remain selectable without editing the Owner's model configuration. Derive the current request's output and thinking reserves from its authorized input and available context, then enforce the same budget at the public Pi stream boundary. Missing capacity still blocks execution.

The driver account must have its own authenticated NapCat forward WebSocket session. Bot and driver identities must differ. Preserve the existing service data and account sessions. Automated regression uses disposable fixtures only. Real acceptance uses the repository's single explicitly designated acceptance service and data directory.

Before real execution, confirm the active checkout, commit, PID, data directory, online accounts, and sole QQ consumer. The `runtime` configuration adds service-manager verification before and after sending, then read-only database correlation by external message ID and exact scope. Match successful Run, authorization decisions, and received reply ID to successful delivery. Missing or uncertain evidence blocks product acceptance. A transport PASS alone does not permit merge.

Schema-v1 free-text live suites remain disabled. Schema-v2 read-only feature suites bind a server restriction to the exact Owner Principal, OneBot scope, canonical message hash, external message and Run. Restrictions expire within 30 minutes, intersect the authorized Tool surface and are rechecked before provider work and protected effects. Unsupported execution origins are rejected. This restriction never grants authority. An unresolved ordinary send writes STOP across runs, as does unconfirmed moderation or lease cleanup. Never clear STOP merely to retry.

Delivery gates: tool tests, `vp run verify:commit`, `vp run verify:full`, then fresh private, group-A and group-B QQ acceptance. Record all results separately. Do not merge before fresh acceptance for the reviewed commit. Standalone systemd Glassbox supervision is not represented by the agent-service registry and must not be claimed as verified by this tool. NapCat and Herdr may remain externally supervised. Runtime evidence requires the exact connectionId and threadId scope, destination scope and delivery Trace ID.

## Expanded delivery requirements

1. A discoverable project skill guides feature selection, environment setup, new-feature acceptance, existing-feature regression, debugging, bounded repair and delivery. It uses glassbox-ops and the root-cause discipline from debug. Stable safety and evidence rules remain separate from mutable, evidence-backed lessons.
2. A maintained feature catalogue maps actual QQ capabilities and affected source paths to executable cases, precise reply/Tool/state assertions, fixture ownership, cleanup and required external prerequisites. Missing implemented-feature coverage blocks a complete regression claim. New functions add their own cases before delivery.
3. Custom feature suites must execute through trusted server-side narrowing for the exact test message identity and scope. The selected Tool surface and call-time actions/resources stay inside both caller authority and case authority. A Prompt or a suite sideEffect field cannot enforce this boundary.
4. Assertions verify actual state and result provenance. A Bot saying it succeeded is insufficient. Positive and negative authorization cases, scope isolation, retrieval, learning, media, group operations and durable work require their own observers and fixtures.
5. Mutable fixtures are explicitly named acceptance resources. Ordinary deterministic tests remain disposable. Real acceptance cleanup verifies both successful operations and interrupted/uncertain operations. Unresolved effects persist STOP and block further sending and merge.
6. The skill can append sanitized, evidence-linked lessons and update secondary procedures after demonstrated failures and successful rechecks. It must never rewrite historical evidence, alter its stable core, remove assertions or promote an unverified hypothesis to a fact.
7. A machine-readable gate combines the selected new-feature suite, complete existing-feature regression coverage, successful cleanup, exact runtime/commit identity, deterministic checks, independent review and GitHub CI. It rechecks the remote PR head immediately before an authorized merge. Any absent or stale evidence blocks merge.
8. After merge, switch the same acceptance service to the merged main commit and repeat the relevant real acceptance. Preserve private reports and record the merged commit separately. Do not claim the final environment is usable until this post-merge round passes.

Environment prerequisites currently include independent logged-in Owner and Bot NapCat sessions, both test groups, the Owner's original StepFun Pi configuration, and consented test subjects for moderation. Expired QQ login requires legitimate account reauthorization. Missing external prerequisites remain explicit blockers while independent implementation and deterministic validation continue.

## Current implementation and remaining acceptance

The new project skill keeps its core hash separate from mutable lessons. Verified lessons require a hashed passing report and matching scoped input/delivery evidence through gbxtrace; evidence without that proof remains a hypothesis.

The feature catalogue inventories implemented descriptors and distinguishes planned cases from runnable cases. Runnable coverage must match the actual suite's leased tools and assertions. Planned coverage and mutations without an implemented cleanup executor remain BLOCKED. The current baseline matrix still needs those executable lifecycle cases.

The local management API registers and revokes read-test restrictions, including idempotent marker revocation after a lost registration reply. Registry state is memory-only. A restarted process cannot reuse a marked message without a live binding. Safe lifecycle and pre-Run denial metadata append to qq-live-acceptance-audit.jsonl; Run evidence stays in Raw Trace. Ordinary messages are unaffected.

Memory lifecycle acceptance uses a unique `qqtest-<32hex>` project fixture. Fixed message builders constrain feedback creation to that project and governance to independently discovered new candidate or Memory handles. A marker-bound, active lease may use the exact reply-marker footer after a Memory command; only the Memory parser removes that footer, while the original message remains in model context and evidence. Wrong or misplaced footer markers fail closed. Read-only fixture discovery checks the Owner, creation Run, first creation audit, project scope and promotion or cleanup audit. Reject and expire preserve test rows and history; they end the fixture's effective state rather than deleting evidence. The fixed memory-lifecycle CLI now connects feedback, promote and expire with independent per-step product and state verification. It checkpoints the marker before lease registration, the receipt before sending, the account-local receipt after sending and state after observations. Checkpoints preserve original Linux process identity, exact private scope, runtime identity and suite hash; atomic publication and replacement retain complete guards after interrupted writes. Run-binding audits carry the actual Run ID, marker and canonical input hash without message payload. It retains an account-wide unresolved-fixture marker after uncertain steps or cleanup. The happy path expires only this fixture and retains audit history. The reconcile-memory CLI inspects interrupted original fixtures without QQ sends, then allows one approved fixed reject or expire cleanup after stopped-process, scoped audit, terminal Trace and read-only product checks. Recovery checkpoints retain original source evidence and separately bind the cleanup process, message and Run. Final independent record and state verification precedes guard release. CLEANED reports are cleanup-only and never satisfy feature acceptance. An interrupted recovery attempt itself remains blocked; automatic takeover and retry are not supported. The fixed three-stage family is bound to schema-v3 suites and the catalogue/gate. Broader Memory lifecycle cases and interrupted-recovery takeover remain pending.

The feature observer checks matching tool call/result pairs and exact Task or Memory resource state with originating Run evidence. History evidence matches the current nonce, the complete group and resource lists, and the retrieval mode without retaining message payload. History search can synchronize the explicitly configured test group's authorized history before applying the nonce query; this remains a real integration action, not a disposable deterministic test. It permits no arbitrary SQL or scripts. The delivery gate requires the complete repository feature catalogue, checks its clean checkout against the target commit before and after inventory, and binds the approved suite's original hash/content, all cases, cleanup, exact commit, fresh product evidence, independent review and current remote CI. The CLI now connects delivery-check and authorized deliver --live to that gate. The GitHub adapter binds checks and formal approvals to the current head, and an exclusive PR-wide attempt record precedes one exact-head squash merge. Unknown results are not retried. Postmerge-check validates the real merge SHA, required CI at that SHA, the original suite and account/runtime identity, and independently observed inputs and Runs after GitHub mergedAt. Local attempt records are advisory evidence, not isolation against equal operating-system access. The full executable baseline remains pending.

Fresh real QQ acceptance, final full verification, PR review/CI for the final implementation, authorized merge and post-merge acceptance remain delivery requirements. Existing provider probes or transport checks cannot satisfy them.

The bounded member-count read case binds Owner private chat to test group A and get_group_member_list. Its observer rejects truncated or unverifiable Tool output, duplicate JSON keys, extra fields, invalid counts and content/details disagreement. A separate fixed Bot-side count read must match the traced projection without retaining or returning member entries. Count changes and uncertain provider responses remain INCONCLUSIVE. This seed does not cover individual member information, role mutations or cross-group isolation. Missing ordinary group authority blocks it; acceptance configuration does not create that authority.

The fixed feedback/reject family requires two distinct Runs and independent Owner, project, candidate creation and rejection audit evidence. Rejected handles cannot contain Memory or promotion identifiers. Its version-3 checkpoint origin binds the fixed family; version 2 retains the original three-stage contract. Schema-v3 suites can declare both families while each invocation selects one. A separately approved recovery cleanup is a new Action with its own marker and Run, never a replay of the original message. These executable cases do not satisfy full Memory scope isolation, Taste or authorization-negative coverage.

The strict history-coverage cases add single-group source and result-window completeness checks to the existing nonce scope. They require the actual source walk to end, no source limits or result truncation, matching per-source and returned-item counts, and the fixed lexical query and limit. Candidate counts remain distinct from returned counts because exact-term, duplicate and other retrieval filters may exclude candidates without truncation. These checks do not substitute for independently proven positive hits, no-hit semantics or cross-group authorization negatives. Those catalogue entries remain planned.

Result-specific history cases additionally compare a new safe result projection with the actual protected Tool output digest. Positive proof binds the archive UUID, external input ID, Owner sender, time and projected body digest to the current group Run. Private no-match proof requires zero scoped archive matches and complete source/window evidence. Historical events are never rewritten, and missing new fields cannot satisfy these cases. Older seeded-message retrieval, isolation and authorization negatives remain pending; the complete regression gate stays blocked until their cases exist and pass.


The fixed history seed family uses one verified group A input and a strictly later Owner-private recall. The source marker, Run and integer-second until bound derive only from the first independently verified step. Both steps require the exact same service identity and version, actual protected output digests, scoped source SQL and revoked temporary leases. Final family verification reconstructs both contracts before counting coverage. It does not cover group B isolation or authorization negatives. Historical verified skill lessons for this two-stage family remain disabled until their separate independent history verifier exists. Real QQ acceptance is still required.


Cross-group history foundations add fixed group B seed and Owner-private group A exclusion constructors. The query marker and B fixture content use separate random identifiers. The exclusion observer requires a complete A-only search with the actual protected Tool output digest, an independently scoped B archive source from the earlier Owner Run, and zero A archive matches within the bound. Actual Bot and driver reply reads reject the fixed B fixture content by digest without returning message bodies. These constructors and observers do not yet constitute executable family coverage. The coordinator, independent final family verifier, suite/catalog binding and real QQ acceptance remain pending. The full delivery gate remains blocked.


Schema 5 adds the fixed history-cross-group-isolation family while preserving the original schema 4 contract. The B seed and A-only private exclusion coordinator stops after uncertain stages and checkpoints before and after each action. Final verification rebuilds both fixed specifications from the actual seed prompt, Run and input seconds, then independently rechecks scoped product, archive, Tool output and actual reply evidence. Both leases must be revoked. Catalogue coverage counts this fixed scope-isolation family only after its independent verifier passes. Revoked-authority negatives and broader history/provider contracts remain pending. Native Pi configuration and locked skill core stay unchanged. Real QQ, final review, full baseline and post-merge acceptance remain required.


Fresh feature verification now requires independent persisted lease registration, scoped Run binding and revocation audit evidence. The same lease, marker, input digest, tool manifest, principal and scope must match, with registration, binding and revocation in timestamp and file order. Missing or malformed evidence stops the CLI and persists STOP before another message. This supplements actual per-message lease receipts and Raw Trace; it does not rewrite historical reports or evidence. Final history verifiers use Recorder actual payload-free reply fields and independently fetched two-account sequence/time/hash bindings, rather than fixture-only reply fields.

Archived history-family lessons require a distinct readonly verifier. Reconstruct the fixed two-stage seed/recall or seed/exclusion contract, independently read successful scoped Runs, ALLOW decisions, stored input and delivered text digests, source archive, gbxtrace and persisted lease cleanup evidence. A verified lesson selects the final stage and rechecks the same clean checkout and service PID before and after readonly inspection. Both accounts must be online to independently re-read existing inputs and replies through a get_msg-only adapter. Config identity, scope and runtime must match; no report digest substitutes for those independent reads. This inspection does not send or modify messages. Replaced-process reports remain hypotheses without independent historical service identity proof. Unsupported payloads and incomplete or downgraded family evidence remain hypotheses. This verifier cannot generate fresh QQ acceptance, count regression coverage or release a delivery gate. Preserve the locked core and append-only sanitized lessons.

Authorization-negative acceptance cannot use acceptance-lease denial as a substitute for normal AuthorizationService DENY. Readonly production-path review identifies a separate fixture group and consented visitor as the isolation boundary for ordinary grant revocation tests. Owner history search filters inactive sources before returning content and may produce an empty search without an explicit denied decision for that source. Same-Run source revocation before terminal delivery has a real delivery_denied and context-exclusion path, but needs its own bounded fixture coordinator, explicit source evidence and no-outbound observer. Those scenarios remain unimplemented and require fixture prerequisites; existing A/B grants must not be silently changed to force a denial.

The fixed group A metadata read extends the baseline without changing ordinary policy or grants. Owner-private qq_groups/get_group_info uses a single exact group:read operation. Its observer verifies complete provider Tool output and matches only the group identity, group-name digest, member count and capacity against a separate fixed Bot read. Raw names and extra provider fields are not retained in observations. Independent unavailable or changed responses remain INCONCLUSIVE. Broader descriptor, mutation and authorization coverage stays planned. Group-info lessons require a separate archived historical witness and currently remain hypotheses. Native Pi settings and both skill cores remain unchanged.

Runtime metadata evidence adds a fixed groupInfo projection from actual protected results and preserves full output SHA256/byte binding without widening the 512-byte Trace head. Both actual account-local replies must satisfy a fixed plain-text count/capacity format and match the independently observed metadata. Old events missing this evidence remain unverified.
