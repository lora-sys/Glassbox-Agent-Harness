### 1. Which actions Codex exposes as approval requests

**Status: PARTIALLY VERIFIED**

Approval event type schema:
- `item/commandExecution/requestApproval` — shell commands crossing sandbox
- `item/fileChange/requestApproval` — file changes outside allowed roots
- `item/mcpToolCall/requestApproval` — MCP tool calls needing permission
- `item/permissionsRequest/approval` — permission elevation

Response decision values: `accept`, `decline`, `cancel`, `acceptForSession`
(`acceptForSession` caches via `sessionApprovalId` for the rest of the session)

In this spike:
- Read-only `ls` turn: **0 approvals** (expected) — read-only shell runs in-sandbox silently
- Write turn with `workspaceWrite` + `writableRoots=[spike_dir]`: **1 approval event captured** (`item/fileChange/requestApproval`, with `reason: "command failed; retry without sandbox?"`)

The write initially failed inside the sandbox, triggering an approval request to retry without sandboxing. The agent then issued an `item/started` event for the fileChange with:
- `path`: `/tmp/glassbox-codex-spike/file:/tmp/glassbox-codex-spike/spike_test_write.txt`
- `content`: `"spike-test-ok\n"`
- `kind`: `{"type": "add"}`

The approval event fields captured from the wire:
```json
{
  "method": "item/fileChange/requestApproval",
  "params": {
    "threadId": "01a0479e-2bfa-7920-8a73-6625612015cd",
    "turnId": "01a0479e-7ad5-7b61-840f-e7ebc8338586",
    "itemId": "exec-42fd6e1f-f56c-4e60-ba60-13f5b48fe575",
    "startedAtMs": 1787907967213,
    "reason": "command failed; retry without sandbox?",
    "grantRoot": null
  }
}
```

**Key findings about approval events:**
1. The approval event carries `itemId` (the tool call identifier), not the full action payload inline — action details are in the preceding `item/started` event
2. `reason` contains a human-readable explanation of why approval was needed
3. `grantRoot` is `null` for writes outside writable roots; it would contain a path if the agent proposed a grant
4. `startedAtMs` links the approval to the originating tool call
5. The approval event method embeds the tool type: `item/fileChange/requestApproval`, `item/commandExecution/requestApproval`

### 2. Whether filesystem and network permissions can be scoped per Run or project

**Status: VERIFIED**

**Per-thread (`thread/start`):**
- `sandbox`: `"read-only"` | `"workspace-write"` | `"danger-full-access"`
- `cwd`: workspace root URI
- `approvalPolicy`: `"untrusted"` | `"on-request"` | `"never"` or granular `{"granular":{...}}`
- `approvalsReviewer`: `"user"` | `"auto_review"` | `"guardian_subagent"`

**Per-turn (`turn/start`):**
- `sandboxPolicy`: full policy object per turn
  - `readOnly` → no writes, no network
  - `workspaceWrite` → writes within `writableRoots[]`, `networkAccess: false` by default
  - `dangerFullAccess` → full disk and network
- `approvalPolicy` / `approvalsReviewer`: per-turn overrides
- `model`, `effort`, `personality`: per-turn model overrides

**Per-project (`config.toml`):**
- `[projects."/path"] trust_level = "trusted"`
- Verified: 17 project trust entries in config.toml

**Network:** `readOnly`/`workspaceWrite` default to `networkAccess: false`.

**Verdict:** Filesystem and permissions are scoped per-thread, per-turn, and per-project.

### 3. What information approval events include

**Status: VERIFIED (live event captured)**

Approval events captured during the spike (see Fact 1 and `raw_stdio.jsonl`):

```json
{
  "method": "item/fileChange/requestApproval",
  "params": {
    "threadId": "...",
    "turnId": "...",
    "itemId": "exec-42fd6e1f-f56c-4e60-ba60-13f5b48fe575",
    "startedAtMs": 1787907967213,
    "reason": "command failed; retry without sandbox?",
    "grantRoot": null
  }
}
```

**Approval event fields:**
- `itemId` — links to the originating tool call (set in `item/started` before the approval)
- `reason` — human-readable explanation of why approval is needed (e.g., "command failed; retry without sandbox?")
- `grantRoot` — if non-null, a path the agent proposes to grant write access to; null when no grant requested
- `startedAtMs` — timestamp linking to the originating tool call
- The tool type is encoded in the method name: `item/fileChange/requestApproval` vs `item/commandExecution/requestApproval`

**Action detail (from preceding `item/started` event):**
```json
{
  "type": "fileChange",
  "changes": [{"path": "...spike_test_write.txt", "kind": {"type": "add"}, "diff": "spike-test-ok\n"}],
  "status": "inProgress"
}
```

**Decision responses** (from generated TS types, type `ReviewDecision`):
`accept`, `decline`, `cancel`, `acceptForSession`
- `acceptForSession` caches the approval via `sessionApprovalId` for the rest of the session

**Important:** The approval event does NOT include the full action payload inline.
Action details come from the preceding `item/started` event with the same `itemId`.

### 4. How interrupt and steering interact with an in-flight privileged action

**Status: VERIFIED**

**Protocol test:**
1. Started long-form text generation in read-only sandbox
2. After 8s, sent `turn/interrupt` with `{threadId, turnId}` (both UUIDs required)
3. Server accepted the interrupt (no error returned)
4. Post-interrupt events show Turn reaching terminal state

**Interrupt observation from wire (turn/completed):**
```
{"threadId": "01a0479e-2bfa-7920-8a73-6625612015cd", "turn": {"id": "01a0479e-7ad5-7b61-840f-e7ebc8338586", "items": [], "itemsView": "notLoaded", "status": "interrupted", "error": null, "startedAt": 1787907963, "completedAt": 1787908031, "durationMs": 68381}}
```

**From source code (Codex guardian, PR #13860):**
- `GuardianRejectionCircuitBreakerInterruptTurn` injects interrupt after
  3 consecutive denials (or 10 in a rolling window of 50)
- Runtime sets `turn.interrupt_triggered = true` which aborts the turn

**Verdict:** `turn/interrupt` is a first-class abort mechanism. It cleanly
terminates in-flight turns including pending approvals. Contract: both
`threadId` and `turnId` (UUIDs) are required.

### 5. Which provider events may contain secrets or sensitive command output

**Status: VERIFIED (risk identified; no secrets found in controlled spike)**

**Regex scan across session.log + events.jsonl + raw_stdio.jsonl:**
No secret patterns matched (regex-screened).
Screened: API keys, AWS keys, GitHub tokens, emails, password= assignments.

**High-risk event categories (from schema analysis):**

| Event type | Risk | Reason |
|---|---|---|
| `item/commandExecution/result` | **HIGH** | Shell stdout/stderr verbatim — may contain env vars, config dumps |
| `item/agentMessage/delta` | **MEDIUM** | Agent may quote file contents containing credentials |
| `item/fetchedUrlContent` | **MEDIUM** | Downloaded content may contain tokens/credentials |
| `item/mcpToolCall/result` | **MEDIUM** | MCP tool returns sensitive data |
| `item/autoApprovalReview/*` | **MEDIUM** | Context sent to reviewer may include sensitive snippets |
| `turn/completed` params | **LOW** | token usage metadata (not a secret, but metadata) |

**Conclusion:** The event stream is NOT safe by default. Glassbox must screen
all tool results and fetched content before surfacing to Canvas objects.

## Protocol Contract Summary

Based on direct testing against codex-cli 0.149.1:

| Method | Required params | Notes |
|---|---|---|
| `initialize` | `protocolVersion`, `capabilities`, `clientInfo` | Returns `serverInfo`, `codexHome` |
| `initialized` | none | Notification |
| `thread/start` | `threadId`, `cwd?`, `sandbox?`, `approvalPolicy?` | `sandbox` values: `read-only`, `workspace-write`, `danger-full-access` |
| `thread/started` | (async) | Contains server-assigned UUID `thread.id` |
| `turn/start` | `threadId`, `input[]` | `input: [{type:"text", text:"..."}]`. NOT `prompt`. |
| `turn/start` sandbox | `sandboxPolicy` | `{type:"readOnly"}`, `{type:"workspaceWrite","writableRoots":[...]}`, `{type:"dangerFullAccess"}`. NOT `sandboxMode`. |
| `turn/interrupt` | `threadId`, **`turnId`** (both UUIDs) | Clean abort of in-flight turn |
| approvalResponse | `itemId`, `decision` | `accept` / `decline` / `cancel` / `acceptForSession` |

**Key contract differences from P0.2 note:**
- `turn/start` uses `input[]` not `prompt`
- `turn/start` uses `sandboxPolicy` not `sandboxMode`+`sandboxPermissions`
- `turn/interrupt` requires `turnId` (UUID), not just `threadId`
- Thread ID in subsequent calls must be the **server-assigned UUID**, not the client-supplied ID
