```
└─────────────────────────────────────────────┘
```

Source: [https://tanstack.com/start/latest/docs/framework/react/overview](https://tanstack.com/start/latest/docs/framework/react/overview)

### SSR modes

Three modes, configured per-route:

- **`ssr: true`** — full SSR. Data and markup arrive ready to hydrate.
- **`ssr: 'data_only'`** — server fetches data but the route component renders client-side.
- **`ssr: false`** — client-only rendering.

### Server functions

Created with `createServerFn()`. Pattern from official docs:

```ts
createServerFn({ method: 'GET' })
  .validator(projectSchema)
  .handler(({ data }) => db.projects.find(data.id))
```

The TanStack Start docs describe a three-tier server boundary model:

1. **Server functions** — typed app calls (the `createServerFn` pattern above; marked `"use server"` internally)
2. **Server routes** — handle external callers (REST/API surface)
3. **Middleware** — composable auth, context, logging, policy

Source: [https://tanstack.com/start/latest/docs/framework/react/overview](https://tanstack.com/start/latest/docs/framework/react/overview)

### Build tooling and runtimes

- **Build tools:** Vite (primary) and Rsbuild (therefore: **Glassbox can provision a Vite-based app**).
- **Deploy targets confirmed:** Cloudflare Workers, Node.js, Netlify, Railway.
- **Peer dependencies (from `@tanstack/react-start` package.json):** `vite >= 7.0.0`, `react >= 18 || >= 19`, `react-dom >= 18 || >= 19`, `@rsbuild/core ^2.0.0`.

## 2. Current status: alpha, beta, RC, stable?

### Stability label: Release Candidate (RC), road to v1 is "quick"

Direct quote from the TanStack Start overview page:

> "TanStack Start is currently in the Release Candidate stage and is considered feature-complete and its API is considered stable. This doesn't mean it is bug-free or without issues, but it does mean that the major features are all in place and the core API is unlikely to change in any significant ways before v1. **The road to v1 will likely be a quick one.**"

Source: [https://tanstack.com/start/latest/docs/framework/react/overview](https://tanstack.com/start/latest/docs/framework/react/overview)

**Interpretation:** RC status with a stated intention to reach v1 quickly. Not released as 1.0 yet, but the API surface is considered stable.

### React Server Components: experimental

RSC support is explicitly labeled "experimental" and requires React 19+, Vite 7+, or Rsbuild 2+. Three helpers power the API: `renderServerComponent`, `createCompositeComponent`, and a route-level `rsc: { enabled: true }` config. Glassbox should treat RSC as non-default.

Source: [https://tanstack.com/start/latest/docs/framework/react/guide/server-components](https://tanstack.com/start/latest/docs/framework/react/guide/server-components)

### Package restructure: confirmed, in progress

The original `@tanstack/start` (v1.120.20, last published 2025-06-08) now delegates to child packages:

```

        @tanstack/start-server-functions-client

        @tanstack/start-server-functions-handler
```

Source: [npm: @tanstack/start dependencies](https://www.npmjs.com/package/@tanstack/start)

Meanwhile, the `@tanstack/react-start` package (v1.168.49 latest as of late August 2026) bundles a wider set:


### v2 or new architecture?

No deprecation notice, no v2 announcement found in any scanned source (docs, npm descriptions, GitHub issues with "deprecation" label). The restructure appears to be an internal package splitting rather than a v1→v2 transition. The TanStack docs still reference Start as a single product with no v2 migration guide.

The only concern: `@tanstack/react-start-rsc` is at v0.1.48, which is pre-1.0 for the RSC sub-package. This is expected since RSC itself is experimental.

**Verdict:** No v2 or radical re-architecture is imminent. The restructuring is a package-internal split designed to serve both React and Solid from shared code, not a breaking change to the public API.

## 3. Which packages should Glassbox use?

### Recommended: `@tanstack/react-start` (the new framework bundle)

For a **new Vite-based project**, the TanStack CLI scaffold produces a project that uses `@tanstack/react-start` as the entry point. This package:
- Re-exports everything a framework consumer needs (client, server, router manifest, SSR, server functions)
- Keeps version numbers aligned across sub-packages (all at 1.16x–1.17x as of late August 2026)
- Is the most active package in the Start ecosystem (1.168.x vs. old @tanstack/start still at 1.120.20 from June 2025)

### What about the old `@tanstack/start`?

- It is **not deprecated** (no deprecation metadata on npm).
- But it is **frozen at v1.120.20 from 2025-06-08** — over 14 months behind the new split packages.
- It acts as a compatibility shim that depends on the split packages internally, but any project importing it directly will not receive newer features or fixes available only in the `@tanstack/react-start` bundle.

### What about `@tanstack/start-plugin-core` and `@tanstack/start-client-core`?

These are **internal** packages consumed by `@tanstack/react-start`. They are not designed for direct consumer use. If Glassbox needs to customize the Vite plugin pipeline or extend the client runtime, these are the right targets, but the normal happy path is to import from `@tanstack/react-start`.

### The correct Vite project scaffolding

```bash
npx @tanstack/cli@latest create
```

This produces a project using:
- `@tanstack/react-start` as the framework
- `@tanstack/react-router` for routing
- Vite as the build tool

An alternative manual install (if you don't want the CLI):

```bash
npm install @tanstack/react-router @tanstack/react-start vite
```

Then configure the `tanstackStart` Vite plugin per the docs.

### Core TanStack packages Glassbox will always need

Regardless of the framework layer, these are the stable, well-maintained packages:

| Package | Status | Role |
|---|---|---|
| `@tanstack/react-router` | Stable, 1.17x | Routing, loaders, search params |
| `@tanstack/react-query` | Stable, 5.x | Server state management (can be integrated with Start via `@tanstack/react-start-query-integration`) |
| `@tanstack/react-start` | RC, 1.16x | Framework layer (SSR, server functions, streaming) |
| `@tanstack/solid-router` | Stable | (if Glassbox ever needs Solid) |

The `@tanstack/react-start-query-integration` exists specifically for wiring React Query into Start's server functions with proper types and context propagation — relevant if Glassbox uses TanStack Query for data management.

## 5. What if TanStack Start is too risky? Fallback options inside TanStack

### Option A: `@tanstack/react-router` + manual Vite SSR (lowest risk)

`@tanstack/react-router` alone (separate from Start) is a **stable, production-proven** router. It provides type-safe routing, loaders, search params, and navigation without any server-side framework.

- **npm:** [@tanstack/react-router](https://www.npmjs.com/package/@tanstack/react-router) (stable, version ~1.17x, same pace as Start)
- **GitHub:** [TanStack/router](https://github.com/TanStack/router)
- **Docs:** [https://tanstack.com/router](https://tanstack.com/router)

Glassbox could use `@tanstack/react-router` for the client-side routing contract, then implement SSR with a custom Vite plugin or middleware layer. This is what many production projects do with TanStack Router today. The tradeoff: you lose the conveniences of Start's built-in server functions, streaming SSR, and plugin system, but you gain stability.

### Option B: `@tanstack/react-router` + `@tanstack/react-query` + custom server

Same as Option A, but add React Query for server state management. This combination covers a large fraction of what Start does, with each piece independently stable:
- React Query is at v5.x and widely adopted.
- React Router is stable and well-tested.
- You'd write your own server function layer or use a lightweight alternative like `nitropack` or plain Express/Cloudflare Workers.

### Recommendation within TanStack ecosystem

If Start proves unstable:
1. **Use `@tanstack/react-router` as the routing layer** (it's the foundation Start is built on, already stable).
2. **Keep `@tanstack/react-start` as a goal**, but version-pin it and track releases.
3. **Monitor v1 tag** — once TanStack Start publishes `v1.0.0`, the risk drops significantly.
4. **DO NOT go without TanStack Router** — it's the product's core innovation (type-safe routing with full URL state serialization) and too valuable to replace.

## Summary risk assessment

| Factor | Assessment |
|---|---|
| Stability | RC — API stable, bugs still being fixed |
| Maintenance | Very active — releases every 1–2 days |
| CLI/templates | `npx @tanstack/cli@latest create` works |
| Package structure | Splitting in progress, but `@tanstack/react-start` bundles everything |
| v1 date | "Quick" per docs, no fixed date yet |
| Fallback | TanStack Router alone is production-stable |

**Bottom line for Glassbox Plan 01:** Using `@tanstack/react-start` as the Start entry point is reasonable. The risk is moderate — the API is stable but the package structure is still settling. The biggest operational risk is between now and the v1.0 release, which could bring minor breaking changes. Version-pinning and tracking releases is recommended. Do not use the old `@tanstack/start` (1.120.20) — it is effectively frozen and will not receive updates.
