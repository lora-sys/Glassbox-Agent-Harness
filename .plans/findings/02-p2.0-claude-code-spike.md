## Summary (Eight Answers)

### Q1. How does T3 Code spawn and drive Claude Code?

**T3 Code uses TWO mechanisms depending on mode:**

**A) Adapter / Interactive mode (sessions, threads, turns):**
- Uses the **Anthropic Agent SDK** (`@anthropic-ai/claude-agent-sdk`) directly
- Calls `query()` from the SDK, which internally spawns the `claude` binary as a subprocess
- Source: `ClaudeAdapter.ts` line ~1712 — `query({ prompt, options: queryOptions })`
- The SDK handles the full lifecycle: process spawn, stdio communication, event streaming
- T3 Code never reads raw stream-json from the adapter; it consumes typed `SDKMessage` objects from the SDK's async iterator
- Key files: `ClaudeAdapter.ts` (4735 lines), `ClaudeDriver.ts` (240 lines)

**B) Text generation mode (commit messages, PR content, branch names):**
- Spawns `claude -p --output-format json` as a subprocess directly
- Pipes prompt via stdin, reads JSON envelope from stdout
- Source: `ClaudeTextGeneration.ts` — `ChildProcess.make()` with `Stream.encodeText(Stream.make(prompt))` piped to stdin
- Uses `--dangerously-skip-permissions` because text generation is fire-and-forget

**Evidence:**
- `ClaudeAdapter.ts:1712` — `createQuery({ prompt, options: queryOptions })` → `query()` from `@anthropic-ai/claude-agent-sdk`
- `ClaudeAdapter.ts:1717` — `import { query } from "@anthropic-ai/claude-agent-sdk"`
- `ClaudeTextGeneration.ts` — CLI subprocess with `-p --output-format json --json-schema ... --dangerously-skip-permissions`

### Q3. Permission model in headless mode

**Permission modes (from `--permission-mode` flag help):**
```
choices: "acceptEdits" | "auto" | "bypassPermissions" | "manual" | "dontAsk" | "plan"
```

**What each mode does (from docs + T3 Code source):**

| Mode | Behavior |
|---|---|
| `default` | Standard interactive: asks for shell/network/file writes, auto-accepts read-only |
| `plan` | Plan-only: agent can only discuss and plan, no tool execution |
| `manual` | Pauses for every tool call (fully supervised) |
| `auto` | Auto-accepts routine actions, asks for riskier ones |
| `acceptEdits` | Auto-accepts file edits (Read/Write/Edit), asks for shell commands (Bash) |
| `bypassPermissions` | No permission prompts whatsoever |
| `dontAsk` | Never prompts; equivalent to full bypass |

**Per-request permission control (for stream-json mode):**

In `--input-format stream-json` mode, you can approve/deny individual tool calls by sending approval messages to stdin:
```json
{"type": "approve", "tool_use_id": "toolu_..."}
{"type": "deny", "tool_use_id": "toolu_..."}
```

This is how T3 Code implements per-request approval: it receives the `assistant` event with `tool_use` blocks, presents an approval card to the user, then sends `approve` or `deny` back via stdin. The SDK's `CanUseTool` callback does the same thing programmatically.

**T3 Code's mapping (from ClaudeAdapter.ts:4268):**
```
T3 "Supervised"    → claude "manual"
T3 "Auto-accept edits" → claude "acceptEdits"
T3 "Auto"          → claude "auto"
T3 "Full access"   → claude "bypassPermissions"
```

**Per-session permission configuration flags:**
- `--permission-mode <mode>` — coarse mode (cannot be changed mid-session without `setPermissionMode()`)
- `--allowedTools "Bash(git *),Read"` — allow specific tools
- `--disallowedTools "Bash,MCP"` — deny specific tools
- `--append-system-prompt <text>` — inject instructions (can include permission directives)
- `--setting-sources user,project,local` — which setting configs to load
- `--settings '{"permissionRules":[...]}'` — inline settings JSON
- `dangerously-skip-permissions` — global bypass (CLI arg only)

**T3 Code per-session surface (ClaudeAdapter.ts:4352):**
```typescript
settingSources: ["user", "project", "local"],  // full config stack
```

**Source:** Live probe + `claude --help`, `code.claude.com/docs/en/headless`, `ClaudeAdapter.ts:4268-4305`

### Q4. Session resume

**`--session-id <uuid>`**: Tags the session with a known UUID. If the session doesn't exist, creates a new one with that ID. If it exists, resumes it.

**`--resume [session_id]`**: Resumes the most recent session (or specific session if ID given). Equivalent to `--session-id` plus resume state.

**`--continue` / `-c`**: Alias for `--resume` — continues the most recent conversation in the current directory.

**`--fork-session`**: When used with `--resume` or `--continue`, creates a new session ID (branching from the existing session).

**How T3 Code implements resume (ClaudeAdapter.ts:1801-1804, readClaudeResumeState:683-714):**
- Stores `resumeSessionId` and `resumeSessionAt` (last assistant UUID) in the session context
- Passes `resume: existingResumeSessionId` to `query()` options
- On session start, builds a resume cursor: `{ threadId, resume, resumeSessionAt, turnCount }`
- The SDK's `query()` passes `resume` to the underlying CLI process
- `readClaudeResumeState()` extracts `resume` (UUID) and `resumeSessionAt` from cursor objects

**What this means for Glassbox:**
- One `claude -p` invocation ≈ one turn (one model request/response cycle)
- Session state is maintained across multiple `-p` invocations via `--session-id` / `--resume`
- `--no-session-persistence` disables disk persistence (in-memory only)
- T3 Code keeps a persistent SDK `query()` session alive across multiple turns via its prompt queue
- T3 Code's approach (persistent process with `query()`) is more efficient than spawning a new process per turn

**Source:** Claude CLI `--help`, `code.claude.com/docs/en/headless`, `ClaudeAdapter.ts:683-714, 1801-1804`

### Q5. Writable-root equivalent

**How Claude Code scopes writes:**

There is no explicit "writable roots" mount like Codex. Instead, Claude Code uses a combination of:

1. **`cwd`**: The working directory. Claude Code's tools resolve relative paths against cwd.

2. **`--add-dir`**: Additional directories the agent can access (beyond cwd).

3. **`--permission-mode`**: Controls whether writes require approval.

4. **`--allowedTools` / `--disallowedTools`**: Tool-level scoping.

5. **`--settings`**: JSON config that can include `permissionRules` for fine-grained path-based rules.

**Safest configuration for one-repo-only access:**
```bash
claude -p --cwd /path/to/repo \
  --permission-mode plan \
  --allowedTools "Read,Bash(git *)" \
  --no-session-persistence
```

Or for write access scoped to one repo:
```bash
claude -p --cwd /path/to/repo \
  --permission-mode acceptEdits \
  --no-session-persistence
```

**T3 Code's approach (ClaudeAdapter.ts):**
- Sets `cwd` per-turn via `queryOptions.cwd`
- Sets `additionalDirectories: [cwd, attachmentsDir]` to grant access beyond cwd
- Does NOT use `--allowedTools` for scoping — relies on permission modes + `canUseTool` callback
- Isolation via `CLAUDE_CONFIG_DIR` env var pointing to a per-instance home directory

**Glassbox should:**
- Always pass explicit `cwd` (never rely on defaults)
- Use `--permission-mode plan` or `--permission-mode acceptEdits` as default
- Not use `--dangerously-skip-permissions` for untrusted code
- Potentially use `--add-dir` to grant access to specific artifact output directories

**Source:** Live testing, `claude --help`, `ClaudeAdapter.ts:4270-4317`, `code.claude.com/docs/en/headless`

### Q6. Which input object is the natural next editable one?

**Options:**
1. **`--append-system-prompt`** — Appends to the default system prompt. Best for Glassbox research context (provenance, provenance tracking instructions, canvas metadata).
2. **`--system-prompt`** — Replaces the default system prompt entirely. Too aggressive.
3. **CLAUDE.md** — Project conventions file. Persistent but user-editable; should not be Glassbox's injection target.
4. **`--settings` JSON** — Inline settings; can include `permissionRules` and other config.
5. **`--add-dir`** — Adds directories to search for CLAUDE.md/skills.

**Recommended: `--append-system-prompt`**

Reasoning:
- It adds to (not replaces) the default system prompt, so Claude's base behavior is preserved
- It's designed for one-shot context injection like Glassbox's runtime metadata
- It's per-invocation, so Glassbox controls it without touching user files
- T3 Code uses `systemPrompt: { type: "preset", preset: "claude_code" }` for the preset, but `--append-system-prompt` would be the Glassbox extension point
- The SDK equivalent is `systemPrompt: { type: "append", text: "..." }` or per-turn context injection

**For Editable Research Inputs (per AGENTS.md):**
- First turn: inject via `--append-system-prompt` with the research input content
- Ongoing: drive edits via `--append-system-prompt` on each resumption
- Priority to mutable inputs: the most recently edited research input should be the one in the prompt

**Source:** `claude --help`, `code.claude.com/docs/en/headless`, SDK docs

## Adapter Design Sketch

### Spawn Model

```
┌─────────────┐     spawn subprocess      ┌──────────────────┐
│ Glassbox     │ ────────────────────────► │  claude -p       │
│ Runtime      │ ◄──────────────────────── │  --output-format │
│             │   stream-json NDJSON      │  stream-json     │
└─────────────┘                           └──────────────────┘
       │
       │ 1. spawn claude -p --output-format stream-json --verbose
       │ 2. parse NDJSON into typed events
       │ 3. accumulate assistant messages (thinking → text → tool_use)
       │ 4. on tool_use → emit Glassbox "approval needed" event
       │ 5. on user decision → write {"type":"approve","tool_use_id":"..."} to stdin
       │ 6. on tool_result → map to Glassbox action event
       │ 7. on result → turn complete, store session_id for resume
```

### Event Mapping Table

| Claude `type` | Claude subtype | Glassbox Event |
|---|---|---|
| `system` | `init` | `session.started` + `session.configured` |
| `system` | `thinking_tokens` | `thinking.progress` (optional) |
| `system` | `api_retry` | `session.retry` |
| `assistant` | (message with thinking) | `agentMessage.start` + `thinking` |
| `assistant` | (message with text) | `agentMessage.delta` / `agentMessage.complete` |
| `assistant` | (message with tool_use) | `action.proposed` |
| `user` | (tool_result, is_error=false) | `action.completed` |
| `user` | (tool_result, is_error=true) | `action.failed` |
| `result` | `success` | `turn.completed` |
| `result` | `error` | `turn.failed` |
| `tool_progress` | — | `action.progress` (heartbeat) |
| `rate_limit_event` | — | `session.rateLimited` (informational) |

### Permission Mapping (Glassbox → Claude)

| Glassbox Mode | Claude `--permission-mode` | Behavior |
|---|---|---|
| supervised | `manual` | Pause for every tool |
| auto-accept-edits | `acceptEdits` | Auto-accept file edits, ask for shell |
| auto | `auto` | Routine auto, risky asks |
| full-access | `bypassPermissions` | No prompts |

Per-request approval: send `{"type":"approve","tool_use_id":"<id>"}` or `{"type":"deny","tool_use_id":"<id>"}` to stdin.

### Session Resume Mapping (Glassbox → Claude)

| Glassbox Concept | Claude Mechanism |
|---|---|
| Thread | One Claude `session_id` (persistent across `-p` invocations) |
| Turn | One `claude -p` invocation |
| Resume from thread | `--resume <session_id>` or `--session-id <session_id>` |
| Disable persistence | `--no-session-persistence` |
| Resumption point | `--resume` alone resumes from last turn |

## Open Questions (Need Owner Judgment)

1. **SDK vs CLI subprocess**: T3 Code uses the Agent SDK (`query()`) for interactive sessions. Glassbox's initial spike could go either way. The SDK handles the full protocol internally; raw CLI subprocess gives more control. Which does the owner prefer?

2. **Event source**: Raw `stream-json` NDJSON (parsed by Glassbox) vs SDK `SDKMessage` async iterator (proven, typed). Raw parsing is more work but requires no SDK dependency. SDK path is proven by T3 Code.

3. **Session persistence**: Should Glassbox create a new session per thread, or reuse/resume across threads? Codex creates threads within sessions. Claude Code creates sessions per directory + auth context.

4. **Writing scope sandbox**: Codex has explicit `writableRoots[]` + LANDLOCK sandbox. Claude Code has only `cwd` + permission modes. Glassbox may need OS-level sandboxing (bwrap/nsjail) to match Codex's guarantee level. Is that in scope for P2.0?

5. **`thinking_tokens`**: Claude Code emits these as separate `system` events in stream-json. They're progress indicators, not content. Should Glassbox surface them in the Canvas, or only use them for telemetry?

6. **Subagent messages**: With `--forward-subagent-text`, subagent text/thinking blocks appear as separate `assistant`/`user` messages with `parent_tool_use_id`. Glassbox should render these inline or as nested objects? (Claude Code 2.1.211+ required)

7. **Permission granularity**: Claude Code's `acceptEdits` mode auto-accepts Read/Write/Edit but asks for Bash. Can Glassbox achieve the same granularity with raw stream-json (per-request approve/deny) without relying on the built-in mode?

8. **MCP server configuration**: T3 Code passes an MCP server config via `--mcp-config`. Glassbox may want to inject its own `--mcp-config` for approval bridging. Is that a P2.x concern?
