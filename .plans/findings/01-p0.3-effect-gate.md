## Schemas Defined

Seven Effect Schema schemas in `apps/server/src/codex/schema.ts`, each wrapping
the `params` object of a JSON-RPC notification with a `_tag` discriminator:

| Schema | JSON-RPC method | Key fields validated |
|---|---|---|
| `ThreadStartedParams` | `thread/started` | `thread.id`, `thread.sessionId`, `thread.status.type`, `thread.cwd` |
| `TurnStartedParams` | `turn/started` | `threadId`, `turn.id`, `turn.status` |
| `ItemStartedParams` | `item/started` | `item.type`, `item.id`, `threadId`, `turnId`, `startedAtMs` |
| `AgentMessageDeltaParams` | `item/agentMessage/delta` | `threadId`, `turnId`, `itemId`, `delta` |
| `ItemCompletedParams` | `item/completed` | `item.type`, `item.id`, `item.status`, `exitCode`, `aggregatedOutput`, `completedAtMs` |
| `TurnCompletedParams` | `turn/completed` | `threadId`, `turn.id`, `turn.status`, `turn.durationMs`, `turn.error` |
| `RequestApprovalParams` | `item/*/requestApproval` | `threadId`, `turnId`, `itemId`, `startedAtMs`, `reason`, `grantRoot` |

All schemas use `Schema.Struct` with the `exact: true` option (where available)
and `Schema.Literal` for the `_tag` field. The `CodexEvent` union is built via
`Schema.Union([...])` over all seven tagged structs.

The `decodeEvent()` function in `decode.ts`:
1. Validates the envelope (`method` string + `params` object) via `Schema.decodeUnknownEffect`
2. Looks up the method → tag via `METHOD_TAG` Map
3. Looks up the tag → individual schema via `TAG_SCHEMA` Map
4. Injects `_tag` into params and decodes via `Schema.decodeUnknownEffect`
5. Returns a `Promise<CodexEvent>` (wraps `Effect.runPromise`) or throws

Error type: `Schema.SchemaError` (Effect v4's `ParseError` equivalent) on
structural validation failures; `Error` on unrecognized methods.

## Adoption Gate Verdict

### 1. Does Effect Schema make the event boundary clearer than plain JSON.parse + runtime checks?

**Yes — clearly, for this path.**

Before: every handler did `(params as SomeShape).someField` which compiles but
provides zero compile-time safety. Accessing `ev.turn.durationMs` without Effect
Schema works but offers no guard against providers adding a field or renaming
one — you get `undefined` at runtime, not a type error.

After: `decodeEvent()` validates the entire params shape at the boundary. A
provider sending `{ turn: { id: ..., status: ..., durationMs: "not-a-number" } }`
throws `SchemaError: Expected number at ["durationMs"]` instead of silently
propagating a string through the system. The `CodexEvent` discriminated union
also lets downstream code switch on `_tag` with exhaustive checking.

The schema definitions are verbose but self-documenting: reading
`ThreadStartedParams` tells you exactly which fields the wire sends, what types
they are, and which are required. This replaces a comment block of field
descriptions in `types.ts`.

**Caveat for this Effect version (4.0.0-rc.112):** Some expected APIs like
`Schema.optionalWith` (defaults), `Schema.UnknownRecord`, and `TaggedUnion` are
missing or buggy. The workarounds (manual `_tag` injection, `Schema.Union`,
`optional` without defaults) add ceremony without adding safety, which narrows
the verdict to "worth it for this one path, but likely not for many paths until
the RC stabilizes."

### 2. Does typed failure (SchemaError) catch malformed events before they become Glassbox state?

**Yes — this is the strongest outcome of the gate.**

The test proves three failure modes:

- **Missing required field**: `{ thread: { sessionId: "x" } }` (no `id`) → throws
  `SchemaError` with `Missing key at ["thread", "id"]`
- **Wrong type for a field**: `{ turn: { id: 123, ... } }` → throws with
  `Expected string at ["id"]`
- **Unrecognized method**: `"turn/does-not-exist"` → throws `Error:
  Unrecognized notification method: "turn/does-not-exist"`

None of these can silently corrupt Glassbox state. The Effect pipeline fails
explicitly with a typed error that identifies the exact field and expected type.
In the adapter, the failure surfaces as a log line with the schema error message
plus falls back to the raw-cast handler so the turn lifecycle is still observed.

### 3. Is the ceremony worth the information for this one path?

**Verdict: Keep Effect for the decode gate at the provider boundary. Limit it everywhere else.**

**Worth it:**
- The typed failure catches exactly the failure mode most likely to cause silent
  bugs at the provider boundary (field name drift, type coercion, missing keys).
- The discriminated union gives exhaustiveness checking downstream.
- 9 lines of handler code (the decode + dispatch switch) replace 20+ lines of
  ad-hoc casts in `collectTurnEvents`, with better error reporting.
- For a system that connects to multiple providers (Codex, others), the
  per-provider schema boundary is the right place — it doesn't leak into generic
  Glassbox state.

**Not worth it (yet):**
- `Schema.optionalWith` (defaults) is missing in this RC, forcing manual
  `default () => ...` in the test and `Union([T, Null])` for nullable fields.
- `TaggedUnion` has a runtime crash in this version.
- The `as` casts needed for `TAG_SCHEMA.get()` and `Effect.runPromise` return
  type inference add friction.
- If you only need `{_tag, ...params}` for dispatch, a hand-written check
  `method in METHOD_TAG` is ~5 lines and zero dependencies. The schema shine is
  in the struct validation, which matters more for complex nested events than
  for flat notification params.

**Bottom line:** Keep the Effect decode gate for the provider boundary. Do NOT
apply it to Canvas state, artifact schemas, or other product layers yet — the
RTK (type-level runtime check, not the Rust Token Killer) penalty grows with
schema complexity, and Effect v4's stable API surface needs to land first.
