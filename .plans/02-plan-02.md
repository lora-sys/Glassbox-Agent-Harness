# Plan 02 — Real work on a real repo, second provider, inputs become editable

Status: DRAFT for owner review. No tickets dispatched until the owner approves this plan.

## Summary

Phase 2 turns Glassbox from a proven prototype into a tool the owner actually uses. The owner picks a real repository under `/data/lora/repos/work/`, connects Glassbox to it through the Claude Code provider, completes a real task, and understands, steers, and edits the run without ever leaving the Canvas.

## Motivation

Phase 1 proved the closed loop on a toy fixture. Three things still separate it from daily use: only one provider exists (codex), the only writable target is a synthetic demo repo, and the only editable research input is the task. The owner's answers to the Phase 2 interrogation settled all three.

## Goal

One sentence: using Glassbox on a real repo from `repos/work`, complete a real task through the Claude Code provider, never leaving the Canvas to understand or intervene with the agent.

## User flow

The owner opens Glassbox, creates a session, picks the provider (claude-code) and a real repo path, and runs a real task. File-change decisions surface on the Canvas and get answered inline. Secrets are screened before anything reaches the Canvas. The owner steers once and edits one input mid-run. Reload reconstructs everything. At the end of the phase the performance redline is measured once and recorded.

## Scope

In scope:
- Thin provider interface extracted from `CodexAdapter` (no generic provider framework)
- `ClaudeCodeAdapter` implementing that interface, modeled on the T3 Code implementation
- Provider picker + real-project entry (repo path selection with guardrails)
- Secret screening as a dedicated slice, enforced at the surfacing layer
- One more research input made editable end to end (edit freely, explicit Apply)
- Token usage fields filled opportunistically
- Performance redline measured once

Out of scope:
- A generic provider abstraction or plugin system
- Artifact as a first-class object (diff views, pinning, revisions)
- Multi-user, remote sessions, persistence beyond the local `.glassbox/` directory
- Any speculative performance optimization

## Settled decisions

From the owner's Phase 2 interrogation (2026-08-30):

1. Phase 2 targets real work on real repos, not more controlled experiments.
2. Second provider comes now: Claude Code. Extract only the adapter interface layer; do not build a provider framework. Copy the T3 Code implementation approach.
3. Input editability outranks artifact upgrades. One more input object becomes editable end to end.
4. Secret screening is a dedicated slice (it is a safety item). Token usage is opportunistic, folded into other slices.
5. A numeric performance redline goes into AGENTS.md, is measured once at acceptance, and no premature optimization happens before it fails.
6. Acceptance sentence: a real task on a real repo, full Canvas flow, no leaving.
7. The demo repo stays as the e2e fixture. The real-project entry is separate.
8. Permission handling is panel-selectable for both providers (codex approval/sandbox policy, claude-code permission mode): the session entry UI passes the mode explicitly, mirroring T3 Code. No silently hardcoded defaults. Vendor T3 Code's relevant sources into `upstream/` and copy proven code from there instead of reinventing.

## Reused mature implementations

- T3 Code as the process reference for driving Claude Code (implementation approach copied, not reinvented)
- Claude Code headless CLI (`claude -p` with stream-json output) as the provider runtime
- Phase 1's schema, trace store, reducer, decision flow, and Inspector, unchanged in shape

## Implementation slices

- P2.0 spike: T3 Code + Claude Code headless protocol study. Findings file with citations, no code.
- P2.1 provider interface: extract the minimal interface from `CodexAdapter` (start session, run turn streaming normalized events, interrupt, respond to a decision, snapshot workspace). Codex moves behind the interface with zero behavior change; all existing tests stay green.
- P2.2 ClaudeCodeAdapter: implement the interface per the spike. Normalize events into the existing schema, trace provenance `claude-code-cli`, map permission requests to the decision flow. Unit tests with recorded fixtures; browser verification for one real turn.
- P2.3 secret screening (dedicated): a screening layer between raw trace and derived state. Patterns for API keys, tokens, env values. Screened content never reaches derived state, Canvas, or Inspector; the raw trace file is never rewritten (evidence rule). Realistic fixtures in tests, including false-positive checks.
- P2.4 real-project entry: provider picker (codex | claude-code), a permission panel, and repo path selection in the session entry UI. The permission panel exposes the modes the spike identified for the chosen provider (codex: approval policy + sandbox policy; claude-code: permission mode) and passes them explicitly with the session, mirroring T3 Code. Guardrails: exactly one writable root, never the Glassbox repo itself, never `~/.glassbox/`. Browser-verified.
- P2.5 input editability: the input object chosen by the spike becomes editable with DRAFT/Apply semantics, explicit action record, and reload replay, matching the S7 pattern.
- P2.6 token usage (opportunistic): map provider usage events from both providers into `traceSummary.tokenUsage`.
- P2.7 performance redline: build or capture a 1,000+ event session, measure select/pan/zoom/inspector latency, record the numbers next to the AGENTS.md redline.
- P2.8 acceptance: the real task on the real repo through claude-code, full Canvas flow, e2e plus owner manual verification, redline checked.

Order: P2.0 -> P2.1 -> P2.2 -> P2.3 -> P2.4 -> P2.5 -> P2.6 -> P2.7 -> P2.8. Secret screening lands before the real-project entry so real repos are never touched unscreened.

## Risky seams

- Claude Code headless approvals may be coarse (permission modes) rather than per-file requests. The panel-selectable permission mode (decision 8) is the accepted answer for the coarse case; whether per-request decision flow is still possible on top is a spike question, not an assumption.
- The provider interface extraction can silently leak codex assumptions (thread/turn lifetime, event field shapes). P2.1 must not change behavior; tests are the guard.
- Permission modes passed from the UI change what a session is allowed to do. The selected mode must land in the trace provenance (which mode was active, when), or a run cannot be reconstructed honestly.
- Secret screening at the surfacing layer means the raw trace on disk still holds secrets. `.glassbox/` is gitignored; the owner accepted evidence preservation over secret-at-rest encryption.
- Real repos contain real state. The writable-root guarantee for Claude Code must be proven on a disposable copy of a real repo before pointing at a real one.
